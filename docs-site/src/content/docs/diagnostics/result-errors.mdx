## `tyc::invalid_question_op`

`?` used in a function whose return type isn't a compatible `Result`:

```python
def f() -> int:
    let n: int = parse_port("8080")?    # ❌ — function returns int, not Result
    return n
```

**Fix:** change the signature, or `match` explicitly.

```python
def f() -> Result[int, str]:
    let n: int = parse_port("8080")?
    return Ok(n)
```

## `tyc::result_error_mismatch`

`?` short-circuits an `Err[E1]` to a function returning `Result[T, E2]` where `E1` is not assignable to `E2`:

```python
def parse_str() -> Result[int, str]: ...

def f() -> Result[int, AppError]:
    let n: int = parse_str()?    # ❌ — str not assignable to AppError
    return Ok(n)
```

**Fix:** convert at the boundary.

```python
def f() -> Result[int, AppError]:
    match parse_str():
        case Ok(n):
            return Ok(n)
        case Err(msg):
            return Err(AppError(message=msg))
```

## `tyc::result_unused` (reserved)

Future-reserved diagnostic for a `Result`-returning call whose value is discarded:

```python
def save() -> Result[None, str]: ...

save()    # would warn: Result not consumed
```

**Not yet emitted by the compiler.** Today, an ignored `Result` is silently dropped; the diagnostic name is reserved so the eventual rule has a stable code from day one. Use [`?`](/Typhon/reference/question-operator/) or `match` to consume `Result` values today.
