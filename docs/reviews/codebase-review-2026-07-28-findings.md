### F1 — [CRITICAL] Emitter never parenthesises operands of `Expr::Compare` or `Expr::If`, re-emitting differently-parsing Python: silent wrong results and a hard SyntaxError from a clean build

**Category:** emit-runtime-crash · **Domain:** emit-sourcemap · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-emit/src/printer.rs:1074`

**Mechanism.** `expr_precedence` (printer.rs:1827) assigns Lambda=1, If=2, BoolOp=3/4, Not=5, Compare=6 — but that table is consulted ONLY by the `Expr::BoolOp` arm (printer.rs:874), the `Expr::BinOp` arm (printer.rs:896-909) and the `Expr::UnaryOp` arm (printer.rs:945). The `Expr::Compare` arm (`Emitter::emit_expr`, printer.rs:1074-1092) emits `c.left` and every element of `c.comparators` with a bare `self.emit_expr(...)`, and the `Expr::If` (ternary) arm (printer.rs:969-975) emits `i.body`, `i.test` and `i.orelse` the same way. Comparison binds tighter than `or`/`and`/`not`, and the conditional expression is right-associative with an `or_test`-only test slot, so any operand whose precedence is below the enclosing form loses its grouping. `BoolOp(Or, [a, b])` sitting in `Compare.left` prints as `a or b == c`, which CPython re-parses as `a or (b == c)`. `If{body: If{..}}` prints as `x if d else y if False else z`, which re-parses as `x if d else (y if False else z)`. `If` in the *test* slot prints as `x if a if b else c else y`, which is not valid Python at all. Because the VM (`tyc run`) walks the Typhon AST directly it keeps the correct grouping, so this is simultaneously a wrong-output bug, a VM/CPython parity divergence, and — in the test-slot shape — an emitted-Python SyntaxError. `tyc build` still reports success in that last case because `format_source`'s parse failure is swallowed by `if let Ok(result) = format_source(...)` at crates/tyc/src/commands/build.rs:1095, so nothing in the pipeline ever re-parses the bytes it wrote.

**Impact.** A user writes a correct, `tyc check`-clean Typhon program using ordinary parenthesised boolean or conditional sub-expressions and `tyc build` silently produces Python that computes a different answer (`r1` flips False→True, `r3` returns 3→1). There is no diagnostic, no warning, and `tyc run` agrees with the source, so the divergence only appears in production. In the ternary-test shape the artifact does not even import, yet `tyc build` exits 0 — the failure lands at deploy time with no signal from the toolchain. This is the exact defect class source maps and the VM-as-drop-in guarantee exist to prevent.

**Suggested fix.** Guard both arms the way `Expr::BinOp` already is. In the `Expr::Compare` arm wrap any operand with `expr_precedence(op) < 6` (i.e. Lambda/If/BoolOp/Not) in parens; note the guard is needed on `c.left` AND every comparator. In the `Expr::If` arm wrap `i.body` when `expr_precedence < 3` (Lambda), wrap `i.test` when `expr_precedence <= 2` (nested If or Lambda — the grammar only allows an `or_test` there), and wrap `i.orelse` when it is a Lambda only if a following token would be ambiguous (orelse is a full `expression`, so a nested ternary there needs no parens). This is purely additive on emitted text — it can only add parentheses, never change an already-correct program. Separately, add a post-emit parse gate: re-parse the final `python_src` with the vendored parser and fail the build (rather than swallowing it) when it does not parse, and stop discarding `format_source`'s Err at crates/tyc/src/commands/build.rs:1095. A regression test asserting `emit_python` output re-parses to an AST equal to the input would have caught all three shapes.

### F2 — [CRITICAL] Instance-attribute assignment (`obj.field = v`, `self.field = v`) is never type-checked — any wrong-typed value silently corrupts a declared field

**Category:** soundness · **Domain:** types-generics · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-types/src/lib.rs:10301`

**Mechanism.** In `check_stmt`'s `Stmt::Assign` arm the per-target dispatch chain handles four target shapes. `Expr::Name` (10212+) re-checks the value against the declared binding type via `c.is_assignable`; `Expr::Subscript` (10326+) checks the element/value type for `list[T]` / `dict[K,V]`; `Expr::Tuple`/`Expr::List` (10314+) go through `assign_unpacking_target`. But the `Expr::Attribute(_)` branch at line 10301 does **only** flow-narrowing bookkeeping — `c.env.clear_attr_narrowing(&path)` then `c.env.narrow_attr(path, value_type)`. It never looks up the receiver's class shape to fetch the field's declared type and never calls `c.is_assignable` / `c.mismatch`. The machinery to resolve the receiver exists and is used two lines earlier (`check_attr_assign_not_frozen` at 10224 resolves the receiver class to fire `tyc::frozen_assign`), so the field type is available — the comparison is simply absent. Worse, the branch then *narrows* the attribute to the wrongly-assigned type, so subsequent reads through the same path are typed by the bad write rather than by the declaration, hiding the error until the value crosses a function boundary. This is also the root cause of the generic variant (`class Box[T]: value: T`, `b: Box[int]`, `b.value = "oops"` accepted).

**Impact.** The declared field type — the foundation of dataclass emission, structural interface conformance, and generic type-argument substitution — carries no write-side guarantee. Any `obj.field = v` or `self.field = v` can install a value of any type, so a `tyc check`-clean program crashes at runtime under both `tyc run` and `tyc build` + CPython. Because attribute writes are the single most common mutation in Typhon (`impl` methods must write through `self.NAME`), this defeats a large fraction of the type system's practical value and silently invalidates every downstream inference that trusts field annotations.

**Suggested fix.** In the `Expr::Attribute(_)` branch at lib.rs:10301, before the narrowing bookkeeping, resolve the receiver type (`infer_expr_readonly(c, &attr.value)`) to a class name, look the attribute up in `c.class_shapes[..].fields` (the same lookup `check_attr_assign_not_frozen` already performs for the frozen check), substitute class type parameters when the receiver is `Type::Generic`, and emit `c.mismatch(&declared, &value_type, span)` when `!c.is_assignable(&declared, &value_type)`. Keep it strictly evidence-gated for additive compatibility: skip when the receiver class is `partial` (venv-introspected), when the field is absent from the shape, when the declared type still contains a free TypeVar (`contains_free_typevar`), when `c.unsafe_depth > 0`, or when the receiver type is `Unknown`/`Any` — so it can only fire on writes the compiler can prove wrong. Also drop the `narrow_attr` to the assigned type when the assignment is rejected, so a bad write cannot re-type subsequent reads.

### F3 — [CRITICAL] Inline `?` in an `elif` condition is lifted between the `if` body and the `elif`, silently reattaching the `elif` to the generated `if isinstance(..., Err)` — wrong branch taken and spurious `Err` returned

**Category:** emit-runtime-crash · **Domain:** types-result · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-syntax/src/preprocess.rs:6022`

**Mechanism.** `rewrite_inline_question_ops_one_line` (preprocess.rs:6022) lifts a `)?` operand into three statement lines — `TMP = call`, `if isinstance(TMP, __typhon_Err__):`, `    return TMP` — pushed into `lifted` (lines ~6055-6057) and emitted by `expand_inline_question_ops` (preprocess.rs:5972) *immediately before* the current physical line, at the same indentation. The pass is purely line-local: it never inspects whether the line it is prefixing is a compound-statement header. When the line is `elif COND:`, inserting statements before it does not produce a syntax error — instead the `elif` silently rebinds to the *generated* `if isinstance(TMP, __typhon_Err__):` guard. Two independent corruptions follow: (a) the fallible call now runs unconditionally, even when the original `if` branch was taken, so an `Err` is propagated on a path that should never have evaluated it; (b) the `elif` body executes whenever the isinstance guard is false, i.e. whenever the call succeeded — regardless of whether the preceding `if` already matched. This is distinct from logged item [20] (ternary / `and`-`or` short-circuit): there the defect is eager evaluation of a syntactically nested operand; here the emitted Python is valid but the `if`/`elif` chain structure itself has been rewritten.

**Impact.** Silent wrong output and spurious error propagation in any `Result`-returning function that uses `?` inside an `elif` condition — a natural shape for validation chains, which is exactly what `Result` is for. `tyc check` is clean and the emitted Python is syntactically valid, so nothing surfaces until the wrong branch is observed in production. `tyc run` cannot be used to catch it either (see the VM inline-`?` finding).

**Suggested fix.** In `rewrite_inline_question_ops_one_line` / `expand_inline_question_ops`, detect that the line being rewritten is a compound-statement header whose lifted statements cannot legally precede it. For `elif` the correct lowering is to rewrite `elif COND:` into `else:` + a nested `if` containing the lifted statements and the original condition; for `while` see the companion finding. As a strictly conservative interim step (additive: it only rejects programs that are already miscompiled), refuse to lift and emit a targeted `tyc::invalid_question_op` variant — the same treatment `?` inside a comprehension already gets — telling the author to bind the fallible call to a `let` before the `if`/`elif` chain.

### F4 — [CRITICAL] VM str/list/tuple search methods silently discard the start/end positional arguments (find, rfind, index, rindex, count, startswith, endswith), producing wrong results and non-terminating scan loops

**Category:** vm-parity · **Domain:** vm-stdlib · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-vm/src/builtins.rs:1352`

**Mechanism.** fn single<'a>(args: &'a [Value], name: &str) at builtins.rs:1352 is `args.first().ok_or_else(...)` - it returns argument 0 and silently ignores every further positional argument rather than rejecting an over-long call. Every member of the string search family routes through it: find (5810), rfind (5821), count (5829), index (5865), rindex (5873), startswith (5808), endswith (5809); the list method table's index (6447) and the tuple table's index (6942) have the same shape. CPython's signatures are str.find(sub[, start[, end]]), list.index(x[, start[, end]]), str.startswith(prefix[, start[, end]]), so the slice bounds are dropped and the search always runs over the whole receiver from offset 0. Two consequences: (a) a wrong integer/boolean is returned with no error, and (b) the canonical `i = hay.find(sub, pos); ...; pos = i + 1` occurrence-scan never advances, so the VM loops forever where compiled CPython terminates. Separately startswith/endswith call .py_str() on the argument, so CPython's tuple-of-prefixes form (name.endswith((".txt", ".py"))) stringifies the tuple and always answers False.

**Impact.** tyc run - the default execution mode - silently computes wrong answers for the most common string-scanning idiom in real programs (tokenizers, log parsers, CSV/prefix matching, path/extension dispatch via endswith(tuple)). Worse, the occurrence-scan loop hangs the VM instead of failing, so a program that works under tyc build && python appears to deadlock under tyc run. Because the divergence is silent, VM-run tests can pass while producing garbage, or vice versa; the VM is documented as a drop-in for the compiled path, so users have no signal the result is untrustworthy.

**Suggested fix.** Purely additive (VM-only, no language-surface change). Add a helper alongside single() - e.g. fn sub_with_range(args, recv) -> (needle, start, end) - that reads args.get(1)/args.get(2), applies CPython's negative-index clamping, and slices the receiver by CHARACTER offsets (consistent with the alpha.3 char-offset fix) before searching, then adds the slice start back onto a found index. Wire it into the find/rfind/index/rindex/count/startswith/endswith arms and the list/tuple index arms. Separately make startswith/endswith match on Value::Tuple and test each element. Consider making single() itself reject args.len() > 1 so future arity drift fails loudly.

### F5 — [HIGH] `gather:` task failure: VM raises the bare exception (catchable), compiled CPython raises an uncaught ExceptionGroup — clean check, opposite outcomes

**Category:** vm-parity · **Domain:** analyse-async · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-vm/src/builtins.rs:4057`

**Mechanism.** `render_gather_block` (tyc-syntax/src/preprocess.rs:7612) lowers the default `gather:` strategy to `async with asyncio.TaskGroup()`. Under CPython 3.13 a TaskGroup whose child task raises re-raises the failures wrapped in a `BaseExceptionGroup` from `__aexit__`, so a surrounding `except ValueError:` does NOT match. The VM's shim takes the opposite path: `create_task` (builtins.rs:4057, inside `make_asyncio_module`) calls `i.force_awaitable(coro)?` and lets the `Unwind::Exception` propagate straight out of the `create_task` call with `?`; the synthetic TaskGroup's `__aexit__` (builtins.rs:4050) is a stub that unconditionally returns `Bool(false)` and never collects or re-wraps anything. There is no ExceptionGroup construction anywhere in the VM. So the identical `.ty` source yields a caught `ValueError` under `tyc run` and an uncaught `ExceptionGroup` under `tyc build && python`. This is not an interleaving-dependent program, which makes it a direct counterexample to the guarantee in docs/vm.md:234. The correct CPython-side handler (`except*`) is itself unmodelled — see the separate finding — so today no `.ty` source text handles a `gather:` failure identically on both surfaces.

**Impact.** A user tests their error handling with `tyc run` (the default, documented iteration loop), sees it work, ships, and the production CPython build dies with an unhandled ExceptionGroup on the first partial failure of any gathered task. Since `gather:` exists specifically for I/O fan-out, partial failure is the expected steady state, not an edge case. There is currently no way to write a handler that behaves the same on both surfaces.

**Suggested fix.** Additive, no surface change: (1) make the VM's synthetic TaskGroup accumulate child failures instead of `?`-propagating them at `create_task`, and have `__aexit__` raise a VM exception of kind `ExceptionGroup`/`BaseExceptionGroup` carrying the sub-exceptions — matching CPython exactly; (2) teach the VM's `except*` handler matching to unwrap groups (see the `is_star` finding); (3) document in docs/language.md §gather and docs/vm.md that `gather:` failures surface as an ExceptionGroup and must be handled with `except*`. A follow-on advice-level lint (`try:`/`except E:` directly wrapping a `gather:` block, no `except*`) would catch the mistake at check time without rejecting anything.

### F6 — [HIGH] String-blind dependency scan silently demotes a whole `gather(strategy="best-effort")` block to sequential awaits, turning captured per-task errors into a crash

**Category:** soundness · **Domain:** analyse-async · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-syntax/src/preprocess.rs:7557`

**Mechanism.** `render_gather_block` (preprocess.rs:7612) calls `gather_has_dependent_bindings` *before* it branches on the strategy, and demotes the entire block to plain `let NAME = await EXPR` lines when any binding looks dependent. Dependency is decided by `expr_references_identifier` (preprocess.rs:7557), a raw byte-level substring scan with an identifier-character boundary test. It runs over the binding's *whole* expression text with no lexical awareness: string literals, attribute names after `.`, and keyword-argument values all count as references. So `posts = fetch_posts("user")` is judged to depend on an earlier binding named `user`, because the four bytes `user` inside the string literal are flanked by `"` (not identifier chars). The consequence is far worse for the best-effort strategy than for the default one: best-effort's contract is that each binding becomes `T | Exception` and the block never raises (`asyncio.gather(..., return_exceptions=True)`). The demotion path emits bare `await`s, so the first failing task now propagates its exception out of the block. The user's explicit `strategy="best-effort"` request is silently discarded, and the failure mode inverts from 'inspect the error value' to 'process dies'. The pass is upstream of the AST, so both the VM and the compiled path are affected identically — this is not a VM divergence but a lowering bug.

**Impact.** Changing an unrelated string literal (a URL kind, a cache key, a log tag) silently strips concurrency AND flips a best-effort gather's error semantics from 'collect' to 'raise'. Nothing warns; the emitted Python looks like deliberately sequential code. The same heuristic also silently de-optimises the default `gather:` strategy whenever a binding name appears in any argument string or as an attribute name (`b = load(ctx.user)` after `user = …`), so users lose the concurrency the keyword exists to provide with no feedback at all.

**Suggested fix.** Two independent hardening steps, both additive: (1) build the dependency scan on the string/comment skip mask the preprocessor already maintains (`scan_line_code_end` / the unified mask added in v0.15.2 for `as!`) so literals are inert, and skip the identifier when it is immediately preceded by `.` (attribute) or immediately followed by `=` in keyword-argument position; (2) never demote a `strategy="best-effort"` block — the user has explicitly asked for `asyncio.gather(..., return_exceptions=True)` semantics, and a genuine dependency there should be a diagnostic, not a silent rewrite to a form with different exception behaviour. Emitting an advice-level diagnostic whenever a demotion occurs would make the remaining (legitimate) demotions visible.

### F7 — [HIGH] `except*` is accepted and type-checked but never validated or modelled: `return` inside an `except*` body emits Python that fails with SyntaxError, and the VM binds the bare exception instead of a group

**Category:** emit-runtime-crash · **Domain:** analyse-async · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-emit/src/printer.rs:679`

**Mechanism.** The vendored Ruff parser produces `StmtTry { is_star: true }` for `except*`. Grepping the whole workspace shows `is_star` is consulted in exactly one place — `tyc-emit/src/printer.rs:679`, where it is forwarded to `emit_except_handler` for round-tripping. No stage validates it, and the VM's `Stmt::Try` interpretation ignores it entirely. Two defects follow. (a) CPython enforces at *compile* time that `break`/`continue`/`return` may not appear in an `except*` body; Typhon has no such check, so `tyc check` reports no errors, `tyc build` reports success, and the emitted `build/main.py` cannot even be imported — `SyntaxError: 'break', 'continue' and 'return' cannot appear in an except* block`. A build artifact that is not valid Python escapes a clean pipeline. (b) Because the VM ignores `is_star`, `except* ValueError as e` binds `e` to the bare `ValueError`, while CPython binds an `ExceptionGroup` wrapping it — so `type(e).__name__`, `e.exceptions`, and any re-raise behave differently. This matters acutely in this domain because `except*` is the *only* CPython-correct way to handle a `gather:` failure (see the ExceptionGroup finding), so the recommended fix for that bug is itself broken on both surfaces.

**Impact.** A green `tyc check` plus a successful `tyc build` produce an artifact that dies at import with a SyntaxError — the strongest form of pipeline-escape defect, and one that CI gating on `tyc check` will never catch. Separately, the only correct way to handle a `gather:` failure silently binds a different object under `tyc run` than under CPython, so `except*` handlers cannot be developed against the VM at all.

**Suggested fix.** Additive and purely rejecting-what-already-crashed (consistent with the alpha.2 precedent): add a conservative diagnostic — say `tyc::return_in_except_star` — fired from the analyse pass when a `StmtTry { is_star: true }` handler body contains `Return`/`Break`/`Continue` at handler-statement level, with a doc page under docs/diagnostics/. Separately, make the VM honour `is_star`: wrap the raised value in an `ExceptionGroup`-kind value at the TaskGroup boundary and have `except*` match/bind the group, so the two surfaces agree.

### F8 — [HIGH] Purity walker ignores comprehensions, f-strings, lambdas and dict/set literals, so `@pure`/`@memo` accept entropy and clock reads and inject `@functools.cache` on nondeterministic functions

**Category:** soundness · **Domain:** analyse-comptime · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-analyse/src/lib.rs:3201`

**Mechanism.** `walk_expr_purity` (lib.rs:3136) is a hand-written partial visitor. It matches only `Await`/`Yield`/`YieldFrom`, `Call`, `BinOp`, `BoolOp`, `UnaryOp`, `Compare`, `If`, `Tuple`, `List`, `Attribute`, `Subscript` — and ends with a bare `_ => {}` catch-all at line 3201. Every other expression kind that can *contain* a call is therefore never descended into: `Expr::ListComp`, `Expr::SetComp`, `Expr::DictComp`, `Expr::Generator`, `Expr::FString`, `Expr::Lambda`, `Expr::Dict`, `Expr::Set`, `Expr::Starred`, `Expr::Named` (walrus), `Expr::Slice`. The entropy/clock/IO gate lives in `forbidden_callee` (lib.rs:3318), which is only ever reached from the `Expr::Call` arm — so a `random.randint(...)` or `time.time()` buried one level inside a comprehension element or an f-string interpolation is never inspected. `check_purity` (lib.rs:2949) then returns `None` (no violation), `analyse_stmts` records `memoise = true`, and the desugarer injects `@functools.cache`. The identical call written at statement level IS caught, which proves the check exists and is being bypassed purely by the visitor gap, not by an intentional carve-out.

**Impact.** `@pure` is documented as a verified assertion ("the six conditions"), and `@memo` is documented as `@pure` plus caching. A user who wraps a random draw, a clock read, a `print`, an `open`, or a `requests.get` inside a comprehension or an f-string gets a silent clean check and a `@functools.cache` decorator on top. The function's observable behaviour changes: the first result is frozen forever, side effects fire once, and the cache grows unboundedly keyed on inputs that no longer determine the output. Because `@memo` is the whole point of the feature and comprehensions/f-strings are the most idiomatic way to write these bodies, this is not an exotic shape. It also undermines `[strictness] auto-memoise` and `[optimise] level = 1`, which silently promote any function that "passes".

**Suggested fix.** Replace the hand-written arm list with an exhaustive traversal. The cheapest correct fix is to make the catch-all a compile error: match every `Expr::` variant explicitly (Rust will then force new AST nodes to be handled), or route through a generic child-visitor helper (`ruff_python_ast::visitor::Visitor` / `Expr::visit_source_order`) and keep `walk_expr_purity` as the per-node predicate. Purely additive: it can only turn a previously-silent `@pure` failure into the `tyc::impure_pure_fn` error it was always meant to be, and per the project's own rule that error only fires on code the docs already declared invalid. Guard the rollout by re-running the example/stress corpus for `@pure`/`@memo` regressions.

### F9 — [HIGH] comptime `int(float)` uses Rust's saturating `as i64` cast, folding a wrong integer constant for any float outside i64 range (and silently converting `inf`/`nan` instead of raising)

**Category:** soundness · **Domain:** analyse-comptime · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-analyse/src/lib.rs:1110`

**Mechanism.** In `eval_call`, the `"int"` arm (lib.rs:1110) folds a float argument with `ComptimeValue::Float(f) => Ok(ComptimeValue::Int(f as i64))`. Rust's `as` cast on f64→i64 is a *saturating* conversion: out-of-range magnitudes clamp to `i64::MIN`/`i64::MAX`, `NaN` becomes `0`, and `±inf` clamps. CPython's `int(float)` is exact truncation into an arbitrary-precision int, and raises `OverflowError` for `±inf` / `ValueError` for `nan`. The same file already knows comptime is 64-bit-limited and guards arithmetic with `checked_add`/`checked_mul`/`checked_pow` + the `COMPTIME_INT_OVERFLOW` diagnostic (lib.rs:1583); that discipline was simply never extended to the `int()` cast, so instead of a clean build error the evaluator silently emits a different number than the program would have computed at runtime.

**Impact.** A build-time constant is silently wrong by ~11 orders of magnitude, with no diagnostic and a green build. Any project folding a float-derived scale factor, byte budget, nanosecond limit, or capacity (`comptime let MAX_BYTES: int = int(float(env("GB", "1")) * 1e9)` grows into this range readily) ships a different program than its source says. `int(inf)` folding to `i64::MAX` is worse: the source is a program CPython would refuse to run, and Typhon turns it into a plausible-looking constant. Comptime's core contract — "the folded value is exactly what CPython would produce" — is violated with no signal at all.

**Suggested fix.** Make the cast range-checked. In the `"int"` arm, reject non-finite floats with a clear message (mirroring CPython's `OverflowError`/`ValueError` wording), and for finite floats compute `f.trunc()` and verify it is exactly representable in i64 (`(-9.223372036854776e18..=9.223372036854776e18).contains(&t)` plus a round-trip `t as i64 as f64 == t` check) before folding — otherwise emit the existing `COMPTIME_INT_OVERFLOW("int() cast")` error pointing at the runtime alternative. This is additive on correct programs: it only turns silently-wrong folds into build errors. Apply the same treatment to the `"float"` arm's `ComptimeValue::Int(n) => ComptimeValue::Float(n as f64)` (also lossy above 2^53, though there CPython is lossy too, so that one is already faithful).

### F10 — [HIGH] auto-parallel-reductions deletes the for statement without checking whether the loop target is read after the loop, so emitted Python raises NameError

**Category:** emit-runtime-crash · **Domain:** analyse-perf · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-analyse/src/reductions.rs:243`

**Mechanism.** match_reduction_loop (reductions.rs:243) enumerates seven eligibility conditions (loop shape, accumulation shape, int accumulator, pure element, invariant iterable, materialisable iterable, unshadowed builtins), none of which considers what the for statement BINDS. rewrite_stmts (reductions.rs:176-183) then does *stmt = build_reduction_stmt(&m), replacing the whole Stmt::For with a single Stmt::AugAssign. Python's for leaks its target into the enclosing function scope and leaves it bound to the last iterated value after the loop completes; the synthesised ACC += sum(map_pure(lambda TARGET: EXPR, ITER)) binds TARGET only as a lambda parameter, which does not escape. Any subsequent read of the loop target (the very common 'for x in xs: ... ; print(x)' / 'return x' shape) therefore resolves to nothing. build_reduction_stmt (reductions.rs:320) never emits a compensating binding, and there is no post-loop liveness scan anywhere in the module. The type checker is unaffected because the rewrite runs during tyc build (crates/tyc/src/commands/build.rs:1038), long after tyc check has approved the program.

**Impact.** A program that type-checks cleanly and runs correctly crashes at runtime the moment the documented auto-parallel-reductions knob is enabled. The failure is a bare NameError in generated code the user did not write, at a line the source map points back at a print(x) that looks perfectly valid in the .ty source. This contradicts the alpha.5 release claim that every rewrite is opt-in or advice-only so no previously-correct program changes behaviour: opting in does break previously-correct programs.

**Suggested fix.** Add an eighth eligibility condition to match_reduction_loop: refuse the rewrite when the loop target name is read anywhere after the for statement in the enclosing scope (a liveness scan over the remaining sibling statements plus enclosing-block tails is sufficient and errs safe). This is purely a narrowing of an opt-in transform, so it is additive-compatible. Emitting a compensating binding is the alternative, but a liveness guard is simpler and avoids reasoning about the empty-iterable case, where the sequential loop leaves the target unbound too. Update the reductions.rs module doc, which currently presents conditions 1-7 as exhaustive.

### F11 — [HIGH] auto-parallel is not gated on free-threading and the documented sys._is_gil_enabled() sequential fallback does not exist, making tyc build -O a ~60x pessimisation on stock CPython

### F14 — [HIGH] tyc migrate injects `let`/`mut` into continuation lines of multi-line signatures and calls, producing .ty files that do not parse (7 of 10 real stdlib modules)

**Mechanism.** `migrate_source` (migrate.rs:95) iterates `source.split_inclusive('\n')` and treats every physical line as an independent statement — it tracks an indent-based scope stack but no bracket depth. `rewrite_line`'s function-body branch (migrate.rs:775-790) therefore fires on any line inside a `def` body that `leading_plain_assign_name`/`leading_ann_assign_name` (migrate.rs:2343, 2165) accept. ### F15 — [HIGH] tyc fmt splits an unparenthesized walrus `:=` into `: =`, destroying a valid, running program in place

**Category:** crash-panic · **Domain:** cli-migrate · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-format/src/lib.rs:748`

**Mechanism.** In `apply_simple_style_rules_with_paren_depth`, the `':'` arm (lib.rs:769-784) correctly declines to insert a space when the next char is `=`, and its comment asserts that the walrus is "handled separately below". But the `'='` arm's guard set is incomplete: `is_augmented` (lib.rs:732-747) enumerates `+ - * / % & | ^ < > ! = @` as preceding chars that keep `=` glued, and omits `':'`; `is_kwarg` is `paren_depth > 0` (lib.rs:748). So for a walrus at paren depth 0 — `while chunk := xs[:2]:` or `if n := len(xs):` — the `=` is classified as a plain assignment, and the arm inserts a space before it (prev is `:`, not whitespace), emitting `chunk : = xs`. A walrus inside parentheses (`if (n := len(xs)) > 3:`) survives only incidentally, because `paren_depth > 0` makes `is_kwarg` true. `format_file` then writes this over the user's source. Compounding it: `run_ruff_format` rejects the corrupted buffer (`exit status: 2`), but `format_source` (lib.rs:124-128) treats a ruff failure as benign, prints a warning, and keeps the corrupted in-process output — so the one signal that the pass produced invalid Python is discarded rather than used to abort. There is no re-parse of the output before write (RELEASE_READINESS_REVIEW.md:301-305 recommended exactly this; only the atomicity half was implemented).

**Impact.** A formatter that destroys source is the worst possible defect class for the tool. `tyc fmt` is documented as the pre-commit step and is run over whole directories; any project using the standard `while chunk := ...:` / `if n := ...:` idiom (Rule 2 explicitly documents walrus as a supported binding form, and the language's own stress corpus uses it) has that file silently converted into a parse error on the next format. Because the write is in place with no backup, recovery depends on version control. The bug is also self-concealing in CI: `tyc fmt --check` reports the file as "would reformat", which reads as normal formatter drift.

**Suggested fix.** Add `Some(':')` to the `is_augmented` match at tyc-format/src/lib.rs:732-747 so a `=` immediately following an emitted `:` stays glued, matching the `':'` arm's stated contract. Separately, stop swallowing a ruff failure: `run_ruff_format` returning `Err` after `can_run_ruff` passed means the in-process pass emitted something ruff cannot parse, which is evidence of corruption — `format_source` should re-parse its own `output` with `tyc_syntax::parse_module` (over the same expanded validation buffer it already builds at lib.rs:84-90) before returning `changed: true`, and return the input unchanged on failure. Both changes only ever preserve source that formatting would have altered, so neither can regress a correct program.

### F22 — [HIGH] f-string interpolation of a brace-opening expression emits `{{...}}`, which CPython reads as escaped literal braces — the expression is never evaluated

**Category:** vm-parity · **Domain:** emit-sourcemap · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-emit/src/printer.rs:1150`

**Mechanism.** In the `Expr::FString` arm of `Emitter::emit_expr` the interpolation branch (printer.rs:1149-1160) writes the opening delimiter unconditionally — `self.write("{")` — and then calls `self.emit_expr(&interp.expression)` with no check on what character that expression starts with. When the interpolated expression is a dict literal, set literal, dict comprehension or set comprehension, `emit_expr` immediately writes its own `{` (printer.rs:981 for `Expr::Dict`, 1001 for `Expr::Set`, 1023 for `Expr::SetComp`, 1034 for `Expr::DictComp`). The two braces become the adjacent pair `{{`, which is f-string syntax for a *literal* `{`. The same happens at the close: the expression's `}` followed by the interpolation's `}` becomes `}}`, a literal `}`. The entire interpolation therefore degrades into literal text. The source form requires a separating space (`f"{ {'a': x} }"`) to parse, and the printer discards that whitespace because it is not carried on the AST. The VM walks the Typhon AST and evaluates the dict normally, so this is also a VM/CPython divergence.

**Impact.** A clean-checking program that formats a dict/set/comprehension inline in an f-string silently prints the *source text* of the expression instead of its value in the built artifact, while `tyc run` prints the correct value. No diagnostic fires. The literal-only case (`f"{ {'a': 1} }"`) coincidentally renders identical text, which makes the bug easy to miss in a smoke test and then surprise in production the moment a variable is involved — log lines, error messages and rendered output become `{'a': x}` instead of `{'a': 42}`.

**Suggested fix.** In the interpolation branch, after `self.write("{")`, insert a single space when the rendered expression would begin with `{` (equivalently: when `interp.expression` is `Expr::Dict | Expr::Set | Expr::DictComp | Expr::SetComp`), and symmetrically insert a space before the closing `}` when the rendered expression ends with `}`. Emitting `f"{ {'a': x} }"` is what CPython and Black both do and is byte-identical for every other expression shape, so the change is additive. A round-trip test that re-parses the emitted f-string and compares interpolation counts would pin it.

### F25 — [HIGH] `tyc::immutable_assign` is disabled for every binding declared inside any loop body — `for …: let x = i; x = 99` compiles clean

**Mechanism.** `Resolver::declare_full` carries a "sequential-loop carve-out" at lib.rs:1052-1071 intended to let a *later sibling loop* reuse a scratch name. Any `BindingKind::Value` binding created while `loop_body_depth > 0` is registered in `loop_origin_spans` (lib.rs:1116-1118). The carve-out then fires on `existing.kind == Value && loop_origin_spans.contains(&existing.span) && loop_body_depth > 0` and **replaces the binding in place and returns** — before reaching the `existing.mutability == Mutability::Let` branch at lib.rs:1085 that emits `tyc::immutable_assign`. The bug is exactly scoped to loop bodies: `loop_body_depth` is incremented only for `Stmt::For`/`Stmt::While` bodies (lib.rs:2198/2217), so the identical code outside a loop is correctly rejected.

Accumulator and scratch variables inside loops are exactly where `let` vs `mut` discipline carries its weight, and exactly where the checker goes silent. Reviewers reading `let total: int = …` inside a loop cannot trust it is single-assignment, and the analyser's purity/parallelisation passes (which reason about `mut` capture) are working from a binding table whose mutability field was silently overwritten by the in-place replace at lib.rs:1060-1064.

**Suggested fix.** Narrow the carve-out so it only covers the case it was written for. This only rejects programs that already violated the documented `let` rule, so it stays additive on correct programs; the sibling-loop scratch-name pattern the carve-out protects keeps working.

### F26 — [HIGH] Mutually-recursive parametric type aliases cause infinite recursion in Checker::is_assignable — tyc check/build/run abort with SIGABRT on a 5-line file

**Category:** crash-panic · **Domain:** robustness · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-types/src/lib.rs:3205`

**Mechanism.** `Checker::is_assignable` (crates/tyc-types/src/lib.rs:3045) unwraps transparent type aliases at lines 3205-3214 and recurses whenever either side changed:

    let exp_unwrapped = self.unwrap_alias(expected);
    let act_unwrapped = self.unwrap_alias(actual);
    if &exp_unwrapped != expected || &act_unwrapped != actual {
        ...
        if self.is_assignable(&exp_unwrapped, &act_unwrapped) { return true; }
    }

The comment claims this "avoids infinite loops on the no-op case" — but it only guards the case where *nothing* changed. `unwrap_alias_inner` (line 3724) carries a `depth >= 8` chain guard, however that guard is useless here: for `type A = list[B]`, `unwrap_alias(Class("A"))` reaches `Generic("list",[Class("B")])` at depth 1 and stops, because the head `list` is not itself an alias. The depth counter then resets to 0 on the next top-level `is_assignable` call.

So the cycle is: `is_assignable(B, A)` -> unwrap -> `is_assignable(list[A], list[B])` -> the same-head generic arm (line ~3256 and the variance arm at ~3484) recurses on the type arguments -> `is_assignable(A, B)` -> unwrap -> `is_assignable(list[B], list[A])` -> `is_assignable(B, A)`. Unbounded. Each level also deep-clones the type through `canonicalize_module_aliases` (line 3540), which is why the gdb frames show `String::clone` inside the malloc that finally faults.

Critically, `detect_cyclic_type_aliases` (line 7274) can never catch this: its `collect_referenced_aliases` helper deliberately treats a reference inside a type constructor's argument list as *guarded* ("recursion through it is productive and legal"), recursing only into `Expr::Subscript.value`, i.e. the head. It is correct that `type Json = str | list[Json]` must be allowed — but the checker's eager alias expansion cannot actually handle the mutual case the pass permits. There is no visited-set and no depth counter anywhere in `Checker::is_assignable`. The pass is also per-file, so the cross-module form is invisible to it by construction.

This is distinct from the logged-pending `assignable()` exponential blowup (audit finding 62), which is *exponential time* on deeply-nested invariant containers in the free `assignable()` function; this is *non-terminating* recursion in the `Checker::is_assignable` method on a cyclic alias graph, with a constant-size input.

**Impact.** A user who writes a pair of mutually-recursive parametric aliases — an entirely natural shape for tree/forest, AST node/attribute, or JSON-like models — gets an uncatchable process abort from `tyc check`, `tyc build` AND `tyc run`, with no diagnostic, no file name, no line number, and no hint at which construct is responsible. The project becomes completely unbuildable and the failure mode gives the user nothing to act on. The cross-module variant is worse: the cycle is split across two files, so the author has no local evidence at all. By shared code path this almost certainly also aborts `tyc lsp`, taking down editor support for the whole workspace on every keystroke that reopens the file.

**Suggested fix.** Add a cycle guard to `Checker::is_assignable`. The cheapest correct fix that respects additive compatibility is a recursion budget plus a visited-pair set threaded through the method (e.g. an inner `is_assignable_inner(&self, expected, actual, seen: &mut HashSet<(Type, Type)>, depth: u32)`), returning the *permissive* answer (`true`) when a pair repeats or the budget is exhausted. Returning `true` on exhaustion means no previously-accepted program is newly rejected — the change can only turn an abort into an accept, never into an error. Separately, `detect_cyclic_type_aliases` (line 7274) could be extended to *warn* (not error) when a guarded cycle spans two or more distinct aliases, since that is exactly the shape the checker cannot expand; but the guard in `is_assignable` is the load-bearing fix and must land regardless, because it also covers the cross-module case the per-file pass can never see.

### F27 — [HIGH] Project file collector follows symlinks with no visited-path guard: a symlink cycle under src/ makes `tyc check` hang indefinitely; a single back-link duplicates every diagnostic 41x

**Category:** performance · **Domain:** robustness · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc/src/commands/util.rs:185`

**Mechanism.** `collect_with_ext_filtered` (crates/tyc/src/commands/util.rs:185) and its unfiltered twin `collect_with_ext` (line 218) walk the source tree with plain `std::fs::read_dir` recursion:

        let entries = std::fs::read_dir(root)...;
        for path in paths {
            if path.is_dir() { /* skip __pycache__, tests, .venv, .dotdirs */ }
            collect_with_ext_filtered(&path, ext, acc)?;   // line 212
        }
    }

`Path::is_dir()` **follows symlinks** (it calls `stat`, not `lstat`). There is no `file_type().is_symlink()` test, no canonicalised visited-path/inode set, and no `max_depth`. Consequently a symlink that points back up into the tree is descended as if it were a real directory.

The only thing that terminates the walk at all is the kernel's `ELOOP` limit (Linux caps path resolution at 40 symlink traversals), which eventually makes `read_dir` fail. That bounds the *depth* at ~40 but not the *branching*: with k symlink back-edges per level the walker enumerates O(k^40) paths. With k=1 it terminates but yields 82 path entries for a 3-file project (the same files re-enumerated under 41 distinct paths). With k=2 it never finishes.

Because the duplicates are distinct `PathBuf`s, every duplicate is preprocessed, parsed, resolved and type-checked again, and its diagnostics are emitted again — `tyc build` reports the same single error 41 times.

**Impact.** A symlink cycle anywhere under `src/` — a monorepo shared-source link, a `current -> .` deploy symlink, a stray `src/vendor -> ..`, or a link created by a package manager — makes `tyc check`/`tyc build` spin forever with no progress output and no way to diagnose it; in CI this burns the whole job timeout. Even a single, entirely benign backward symlink (which the user may not even consider part of the source tree) inflates the file count 27x, multiplies compile time by the same factor, and makes `tyc build` print every diagnostic 41 times, which is enough to make the error output unusable. Note that the existing `.venv`/`__pycache__`/`tests`/dotdir skips do not help, because those are name-based and a link named anything else is descended.

**Suggested fix.** In both `collect_with_ext_filtered` (line 185) and `collect_with_ext` (line 218), (a) use `std::fs::symlink_metadata` / `DirEntry::file_type()` rather than `Path::is_dir()` so symlinked directories are identified, and (b) maintain a `HashSet<PathBuf>` of `canonicalize()`d directories already visited on the current walk, skipping any directory already present. Either alone fixes the hang; both together also stop the duplicate-file amplification. A `max_depth` backstop (say 64) is a cheap third belt. This is purely a file-enumeration change and cannot alter the accepted language surface. As a second-order cleanup, deduplicate `acc` by canonical path before the check loop so a legitimate symlinked source directory is still checked exactly once.

Emitting `@runtime_checkable` on interface Protocols is NOT sufficient — it checks attribute presence only and would silently accept a wrong-signature object.

**Mechanism.** The LSP has its own introspection implementation, separate from the `tyc-venv` crate that the alpha.3 `TYC_NO_INTROSPECT` work hardened. `IntrospectionCache::for_project_root` (tyc-lsp/src/venv_introspect.rs:111) picks `<root>/.venv/bin/python` or falls back to `which_python3()` (:209) with **no** `std::env::var_os("TYC_NO_INTROSPECT")` check anywhere in the file — compare `tyc_venv::discover_python` (tyc-venv/src/lib.rs:307), which returns `None` on that variable. `IntrospectionCache::members` (:151) then calls `introspect_via_python` (:369), which spawns the interpreter with the embedded `INTROSPECT_SCRIPT` on stdin; that script runs `importlib.import_module(name)`, executing the target module's top-level code. Critically, unlike `tyc_venv::VenvSignatures::module_shapes` (tyc-venv/src/lib.rs:271), which gates on `self.allowed_top_level.contains(top)` derived from `typhon.toml` `[dependencies]`, the LSP path applies **no allow-list at all** — any bare dotted name in an `import` statement is imported. SECURITY.md:47-49 states "**`TYC_NO_INTROSPECT=1`** disables venv dependency introspection entirely, in both the CLI and the language server" — that guarantee is false for the code path that actually runs on file open.

**Impact.** Cloning an untrusted Typhon repository and opening one of its `.ty` files in VS Code (or any LSP client) is remote code execution with the developer's full privileges, at file-open time, with no prompt. The documented mitigation a security-conscious user would reach for — `TYC_NO_INTROSPECT=1`, which SECURITY.md explicitly says covers the language server — provides no protection, so users who follow the documented safe-inspection procedure are exposed while believing they are not. The absence of the `typhon.toml` allow-list widens the target from "declared dependencies" to "any importable name", including attacker-supplied `.py` files committed alongside the `.ty` source.

**Suggested fix.** Two independent fixes, both additive: (1) In `IntrospectionCache::for_project_root` and in the venv re-discovery branch of `members` (tyc-lsp/src/venv_introspect.rs:111 and :166), return/keep `python_bin = None` when `std::env::var_os("TYC_NO_INTROSPECT").is_some()` — or better, delete the duplicated discovery entirely and call `tyc_venv`'s already-gated `discover_python`, which is the whole point of the crate extraction. Add a regression test asserting no subprocess is spawned with the variable set. (2) Give the LSP path the same `allowed_top_level` gate `tyc_venv::VenvSignatures::module_shapes` uses (read `[dependencies]`/`[dev-dependencies]` from `typhon.toml` plus the stdlib set) so an undeclared name is never imported; today a name absent from the manifest is imported by the LSP while `tyc check` refuses it, which is also a correctness inconsistency. Consider additionally passing `.current_dir()` of a scratch directory and `-I`/`-P` to the introspection subprocess so a repo-local `.py` is not on `sys.path`. SECURITY.md should not be relaxed to match the bug — the documented behaviour is the correct one.

### F32 — [HIGH] Emitter's triple-quoted-string escaper ignores a quote run at the tail, so an ordinary .ty string literal either silently loses characters (VM/CPython divergence) or emits Python that fails to parse

**Category:** emit-runtime-crash · **Domain:** security · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-emit/src/printer.rs:1926`

**Mechanism.** `Printer::emit_expr`'s `Expr::StringLiteral` arm (tyc-emit/src/printer.rs:1269-1304) switches to a triple-quoted form whenever the source used triple quotes **or the value contains a literal newline** (`use_triple`, :1291-1292), then writes three `quote` chars, `escape_triple_quoted_string(text, quote)`, and three more `quote` chars. `escape_triple_quoted_string` (:1926) tracks a `run` counter and escapes only the *third* consecutive delimiter inside the content — it never accounts for the closing delimiter that the caller appends immediately after. A value ending in one unescaped quote therefore emits `"""…"` + `"""` = four consecutive quotes: CPython closes the literal at the first three and the stray fourth opens an unterminated single-quoted string → `SyntaxError`. A value ending in two unescaped quotes emits five: CPython closes at the first three and treats the trailing `""` as an adjacent empty literal via implicit concatenation → the file parses, but the two trailing quote characters are silently deleted from the value. The VM (`tyc run`) walks the Typhon AST and never goes through this printer, so it produces the correct value — making the two-quote case a silent `tyc run` vs `tyc build && python` divergence. Both cases arise from completely idiomatic Typhon (`"line1\nType \"yes\""`), and `tyc check` and `tyc build` both report success.

**Impact.** Case A turns a green `tyc build` into a shipped artifact that cannot even be imported — the compiler's core promise ("every .ty file emits valid .py") is violated by a string literal a user would write without a second thought (prompts, SQL, JSON templates, any multi-line message ending in a quoted word). Case B is worse in kind: the program runs, produces wrong data, and `tyc run` disagrees with `tyc build && python`, so local testing on the VM cannot surface it. Because the trigger is `value contains a newline`, it fires on plain single-quoted `"...\n...\""` literals, not just author-written triple-quoted strings. ruff format does not rescue Case A — the broken text ships with `[emit] format = true`.

**Suggested fix.** In `escape_triple_quoted_string` (tyc-emit/src/printer.rs:1926), after the loop, escape any trailing run of delimiter characters — e.g. if the output ends with one or more `quote` chars, backslash-escape the final one (or all of the trailing run) so no content quote can merge with the appended closing delimiter. Equivalently, treat the closing delimiter as three more delimiters for the purposes of the `run` counter. A tighter belt-and-braces option is to fall back to the single-quoted `escape_python_string_with_quote` path when `text.ends_with(quote)`. Add unit tests for content ending in exactly one and exactly two delimiter chars, and a pipeline test that parses the emitted file. This is a pure emit fix: it changes no accepted surface and only makes previously-broken output correct, so it satisfies the additive-compatibility constraint.

### F33 — [HIGH] `enum` body member rewrite runs on lines inside triple-quoted strings, silently mutating string constants and docstrings

**Category:** emit-runtime-crash · **Domain:** syntax-preprocess · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-syntax/src/preprocess.rs:361`

**Mechanism.** In `preprocess_opts`, once an `enum Name:` header sets `enum_header_indent` (preprocess.rs:786), every subsequent line with `indent_len > header_indent` is treated as an enum member (preprocess.rs:361–388). The membership test is purely indentation; the loop never consults `in_string`. Worse, the branch `continue`s at preprocess.rs:359/384/387 *before* reaching the single site that advances string state — `rewrite_optionals(&line_after_keyword, &mut in_string)` at preprocess.rs:988 — so `in_string` is never updated for any line in an enum body. Two consequences: (1) a line of triple-quoted-string *content* that happens to be a bare identifier matches `is_bare_member` (preprocess.rs:367–375) and gets ` = enum.auto()` appended into the middle of a string literal; (2) a triple-quoted string opened inside the enum body is invisible to the rest of the pipeline, so when a string-content line dedents to/below the header indent the body is declared finished and the closing `"""` is re-processed as an *opening* quote, desynchronising `in_string` for the remainder of the file and suppressing the `T?` → `T | None` rewrite.

**Impact.** A user's string literal / docstring silently ships with compiler-injected text (`= enum.auto()`) that they never wrote — wrong help text, wrong CLI usage banners, wrong protocol payloads — with a clean `tyc check`, a clean `tyc build`, and identical wrong output on both the VM and CPython paths, so no cross-check catches it. The second form rejects a perfectly valid program with a `tyc::parse` error pointing at unrelated code, which violates the project's additive-compatibility guarantee.

**Suggested fix.** Thread `in_string` through the enum-body branch: compute the line's entry string state *before* the membership test and skip both the member rewrite and the body-termination test whenever `in_string.is_some()`; and replace the three early `continue`s with a path that still advances `in_string` for the emitted line (e.g. call `scan_line_code_end`/`rewrite_optionals` on the verbatim line before `continue`). ### F34 — [HIGH] `with`-chain body re-indentation strips leading whitespace from triple-quoted string content, silently changing string values

**Category:** emit-runtime-crash · **Domain:** syntax-preprocess · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-syntax/src/preprocess.rs:7334`

**Mechanism.** `render_chain` lowers a `with a = f()?:` chain by hoisting the block body up one indent level: it computes `inner_indent = chain_indent + unit_indent` (preprocess.rs:7272) and then, for every collected body line, does `line.strip_prefix(inner_indent)` and re-emits it at `chain_indent` (preprocess.rs:7334–7346). `chain.body` is a `Vec<String>` of raw physical lines gathered by `collect_chain`; nothing distinguishes a line of Python code from a physical line that is *inside* a triple-quoted string literal. For string-content lines the leading whitespace is part of the string value, so stripping it silently rewrites the constant. Because the rewrite happens in the preprocessor, both the compiled path and the tree-walking VM consume the mutated text, so VM/CPython cross-checking cannot reveal it.

**Impact.** Any multi-line string literal written inside a `with`-chain body — SQL, YAML/TOML fragments, JSON payloads, help text, generated code, whitespace-significant templates — is silently re-indented by the compiler. `tyc check` is clean, `tyc build` is clean, and the VM reproduces the same wrong value, so there is no signal at all. For whitespace-sensitive payloads (YAML, Markdown code fences, Python source emitted by the program) this is a correctness bug that can only be found by diffing runtime output against source.

**Suggested fix.** Have `collect_chain` record, per body line, whether the line began inside a triple-quoted string (it already tracks `in_string` via `scan_line_code_end` at preprocess.rs:6936 — just capture the flag), and have `render_chain` emit such lines byte-for-byte verbatim instead of applying `strip_prefix(inner_indent)`. Same treatment for `chain.else_body` before `rename_whole_word` (preprocess.rs:7307–7309), which would otherwise rename identifiers appearing in string content.

### F35 — [HIGH] Indent-only block collection in `collect_chain` and `expand_impl_sealed_unions` is blind to triple-quoted strings, rejecting valid programs with bogus `tyc::parse` errors

**Category:** false-positive · **Domain:** syntax-preprocess · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-syntax/src/preprocess.rs:6933`

**Mechanism.** Both block collectors decide where a block ends solely from leading whitespace. `collect_chain` (preprocess.rs:6922–6939) breaks the `with`-chain body at the first non-blank line whose `indent_len <= chain_indent.len()`; `expand_impl_sealed_unions`' body probe (preprocess.rs:1902–1916) breaks at the first line whose `cand_indent <= indent_len`. Both call `scan_line_code_end(raw, &mut in_string)` *after* the indent test, so the tracked string state is computed but never consulted. A physical line that lives inside a triple-quoted string but starts at (or left of) the block's own column therefore terminates the block mid-literal. `collect_chain` then hands a truncated body to `render_chain` (which re-indents it) while the remaining string lines stay at their original indent; `expand_impl_sealed_unions` duplicates the truncated body once per union variant, physically splitting the string literal across the duplicated blocks. Additionally, `collect_chain`'s `else`-header probe (preprocess.rs:6951–6957) matches any line at the chain indent starting with `else `, so string content of the form `    else foo:` is consumed as a real `else err:` header.

**Impact.** A valid program is rejected outright. The trigger — a triple-quoted string whose interior lines are not indented past the enclosing block (ubiquitous for SQL, usage banners, embedded config, ASCII art, generated source) — is ordinary Python style, and the resulting diagnostic points at unrelated lines, sometimes rendering compiler-synthesised source the user never wrote, so it is very hard to diagnose. This is the project's declared worst-case defect class (false positive on previously-correct code).

**Suggested fix.** In both scanners, evaluate the *entry* string state for each candidate line before the indent comparison and unconditionally treat a line that starts inside a triple-quoted string as block content (never a dedent, never an `else` header). `collect_chain` already carries `in_string`; `expand_impl_sealed_unions`' probe loop needs its own `scan_line_code_end` state seeded from the header line. This only widens what is accepted, so it cannot break a currently-correct program.

### F36 — [HIGH] Multiple-inheritance constructor field order uses base declaration order, not CPython's reverse-MRO — silently scrambles positional constructor arguments and can crash at import

**Category:** emit-runtime-crash · **Domain:** types-classes · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-desugar/src/lib.rs:4007`

**Mechanism.** CPython's `@dataclass` builds its field list by walking `cls.__mro__[-1:0:-1]` — reverse MRO — so for `class C(A, B)` the fields of **B** are inserted before those of **A**. Two places in Typhon assume the opposite. (1) `inherit_parent_fields` (tyc-desugar/src/lib.rs:3955; base loop at :4007) walks `c.bases()` left-to-right and prepends each parent's `AnnAssign` fields into the child body in that order, producing a body of `[A-fields, B-fields, own-fields]`. (2) `effective_class_shape` (tyc-types/src/lib.rs:8897; base loop at :8921) does the same left-to-right merge to build the `field_order` that `class_constructor_arity_for` (:9163), `missing_required_fields` (:9021) and `check_concrete_constructor_args` (:1000) all use to bind positional constructor arguments. Re-declaring the inherited names inside the child body does NOT fix the order: `dataclasses._process_class` seeds `fields` from the bases first, and re-annotating an existing name only overwrites the value in a dict whose insertion order is already fixed. So the checker binds positional arg *i* to `field_order[i]` (A-first) while the emitted `__init__` binds it to the reverse-MRO slot (B-first). The same divergence flips the default-ordering picture: `tyc::field_default_ordering` is computed over the A-first order and passes shapes that CPython rejects outright. The VM (`tyc run`) follows the checker's order, so it silently produces a *third*, different answer.

**Impact.** A program that passes `tyc check`, `tyc build` and `tyc run` writes every positional constructor argument of a multiply-inheriting class into the wrong field, with no diagnostic and no exception — the worst possible failure mode (silent data corruption that survives all three toolchain surfaces and only shows up as garbage downstream). The variant in repro B turns into a hard `TypeError` at module import, i.e. a build that cannot run at all despite a green check. Multiple inheritance is a first-class supported form here (tyc-desugar carries dedicated `class_has_multiple_concrete_bases` / `multi_base_parents` logic at lib.rs:2106 to suppress `slots=True` for exactly this shape), so this is not an unsupported-syntax edge.

**Suggested fix.** Compute a real C3 linearisation once and share it. In `tyc-desugar::inherit_parent_fields`, walk the linearised bases in *reverse* MRO order when building `inherited` (so B's fields precede A's for `class C(A, B)`), and mirror the identical order in `tyc-types::effective_class_shape` so `field_order` and the emitted `__init__` agree by construction. Extract the linearisation into one helper consumed by both crates to prevent re-drift. This is additive-safe: every program it changes is one that is *currently* mis-binding arguments or failing at import, so no previously-*correct* program shifts. If a full C3 walk is judged too invasive for a patch release, the conservative interim is a new error-level diagnostic that rejects **positional** construction of any class with 2+ concrete field-carrying bases (keyword construction is already order-independent and correct), plus extending `tyc::field_default_ordering` to evaluate the reverse-MRO order — both fire only on code that already crashes or corrupts.

### F38 — [HIGH] `Checker::is_assignable` has no Union/Union arm — `Dog?` is not assignable to `Animal?` (nor `Button?` to `Drawable?`, `Circle?` to a sealed `Shape?`, `UserId?` to `int?`)

**Category:** false-positive · **Domain:** types-core · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-types/src/lib.rs:3341`

**Mechanism.** The free `assignable()` (line 274) documents at lines 303-310 that the `(Union, Union)` arm MUST come before the single-Union arms, because otherwise `(Union, other)` followed by `(other, Union)` degenerates into "every actual variant must match EVERY expected variant". `Checker::is_assignable` — the nominal-aware layer that adds class inheritance, interface conformance, sealed-union membership and newtype/alias unwrapping — reproduces only the two single-Union arms (lib.rs:3341 `if let Type::Union(variants) = expected { return variants.iter().any(|v| self.is_assignable(v, actual)) }` and lib.rs:3346 for the actual side) and omits the Union/Union arm entirely. Both are unconditional early `return`s. So for `expected = Animal | None`, `actual = Dog | None`: the free `assignable` correctly fails first (it has no inheritance knowledge — `assignable(Animal, Dog)` is false), control reaches lib.rs:3341, and the expected-Union arm asks `is_assignable(Animal, Dog|None)` and `is_assignable(None, Dog|None)`. Each of those hits the actual-Union arm at 3346, which requires *all* actual variants to satisfy that single expected variant — `is_assignable(Animal, None)` is false, `is_assignable(None, Dog)` is false — so both candidates fail and the whole check returns false. The correct rule (the one the free layer implements) is: every actual variant must be accepted by *some* expected variant. The bug is invisible for pure-primitive unions (`int? → float?` succeeds inside the free layer at line 308) and invisible when every actual variant conforms to one single expected variant (`Dog | Cat → Animal` succeeds), which is why it survived the corpus: it fires exactly when the union contains `None` (or any second variant) alongside a value needing nominal subtyping — i.e. the canonical `T?` shape.

**Impact.** Any function returning `Subclass?` / `Variant?` / `Impl?` / `Newtype?` cannot be stored in, passed to, or returned from a slot typed with the corresponding supertype-optional — the single most idiomatic Typhon shape (`T?` is the language's headline nullability feature, and sealed unions + structural interfaces are the two recommended abstraction mechanisms). There is no clean workaround: the author must either widen the producer's return type by hand, insert a redundant `if x is None` split, or reach for `as!`/`unsafe:`, all of which lose information. Because `tyc::type_mismatch` is an error, this blocks `tyc check` and `tyc build`.

**Suggested fix.** Mirror the free layer: insert a `(Type::Union(exp_vs), Type::Union(act_vs))` arm in `Checker::is_assignable` immediately *before* the existing expected-Union arm at lib.rs:3341, implemented as `act_vs.iter().all(|a| exp_vs.iter().any(|e| self.is_assignable(e, a)))`. This is a pure relaxation (it can only turn `false` into `true`), so it cannot reject any previously-accepted program and is additive-compatible. Longer term the duplicated arm set between `assignable` and `Checker::is_assignable` should be unified behind one traversal parameterised by a nominal-knowledge callback, since the READ_VIEW/Mapping/Function/Result/tuple_variadic arms are all duplicated today and this is the second drift they have produced.

### F39 — [HIGH] READ_VIEW_HEADS over-approximates the abc lattice: `set`/`frozenset` satisfy `Sequence[T]`/`Reversible[T]` and `list`/`tuple`/`set` satisfy `Iterator[T]` — clean check, `TypeError` at runtime in both CPython and the VM

**Category:** soundness · **Domain:** types-core · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-types/src/lib.rs:378`

**Mechanism.** The B31 read-view covariance rule is spelled twice — in the free `assignable` at lib.rs:370-384 and again in `Checker::is_assignable` at lib.rs:3355-3368 — and both use one flat cross-product: `READ_VIEW_HEADS = [Sequence, Iterable, Iterator, Collection, Container, Reversible]` × `{list, tuple, set, frozenset}`, returning `assignable(elem_expected, elem_actual)` for *any* pairing. That is wrong for three of the twelve cells. (1) `set`/`frozenset` are NOT `Sequence` — they have no `__getitem__`, so `s[0]` raises `TypeError: 'set' object is not subscriptable`. (2) `set`/`frozenset` are NOT `Reversible` — `reversed(s)` raises `TypeError`. (3) `list`/`tuple`/`set`/`frozenset` are NOT `Iterator` — they are `Iterable` but have no `__next__`, so `next(xs)` raises `TypeError: 'list' object is not an iterator`. CPython's `collections.abc` registers these distinctions precisely (`set` registers on `Set`/`Collection`, not `Sequence`; `Iterator` requires `__next__`), and typeshed/mypy/pyright all reject these assignments. The rule is a bare head-name table with no per-head guard, so nothing narrows it. Note this is the opposite direction from the already-logged pending item [51] (which is about the lattice being too *strict* for `Sequence → Iterable`); the over-permissive cells are separate and unlogged.

**Impact.** A `set` passed to a `Sequence[T]` parameter, or a `list`/`tuple` passed to an `Iterator[T]` parameter, type-checks clean and then crashes at runtime with `TypeError`. Both are natural author mistakes (`Sequence` is the recommended covariant read-only parameter type — the `tyc::type_mismatch` help text for `list[T]` invariance explicitly tells users to "use `Sequence[int]` (covariant, read-only) on the parameter", so users reach for it constantly; and `Iterator` vs `Iterable` is the classic confusion the type checker exists to catch). The failure is a hard crash in production Python, not a silently-wrong value, and both the compiled path and the VM agree — so there is no parity signal either.

**Suggested fix.** Replace the flat cross-product at lib.rs:378-384 and lib.rs:3363-3368 with a per-head admissible-actual table: `Sequence` ⇒ {list, tuple}; `Reversible` ⇒ {list, tuple}; `Iterator` ⇒ {} (no builtin container is an iterator; keep the existing user-class `__next__`+`__iter__` structural path at lib.rs:3420 as the only way in); `Iterable`/`Collection`/`Container` ⇒ {list, tuple, set, frozenset} (unchanged, and ideally widened to `dict`/`str`/`bytes`, which is pending item [51]). Removing cells narrows the accepted surface, so it needs the additive-compatibility carve-out already used for `tyc::not_a_context_manager` / H5: the three cells being removed accept only programs that were already guaranteed to raise `TypeError` at runtime, which is exactly the alpha.2/alpha.4 precedent. Ship it with a `docs/diagnostics/*.md` note and a CHANGELOG entry flagging the narrowing.

### F40 — [HIGH] `Type::Function` records no required-arity, so a function with a defaulted parameter is rejected where `Callable[[...], R]` is expected

**Mechanism.** `Type::Function { params, ret, variadic }` (lib.rs:52-60) models arity as a single `params` vector plus a `variadic` flag that is set *only* for `*args`: the function-type constructor at lib.rs:9232 is literally `variadic: parameters.vararg.is_some()`. **Category:** soundness · **Domain:** types-generics · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-types/src/lib.rs:15464`

**Mechanism.** Two independent design choices combine into a hole. (1) In the call-argument loop at lib.rs:15456, each positional argument is checked against `expected = params[i].clone()` (line 15464) — the **declared, un-substituted** formal. For `def add_all[T](dst: list[T], src: list[T])` that is `Generic("list", [TypeVar("T")])`, and `assignable` treats a `TypeVar` leaf as permissive, so the `is_assignable` guard at 15508 accepts *any* `list[X]`. Each argument is validated in isolation; nothing ever re-validates the actuals against the formals after inference has pinned `T`. (2) `bind_typevars_checked` (lib.rs:1887), on encountering a second, conflicting binding for the same name, does `bindings.insert(name, Type::union_of(vec![existing, other]))` at lines 1946-1948 — it *widens* rather than reporting an inconsistency. That widening is the documented behaviour for scalar params (`pair(1, "two")` → `T = int | str`) and is sound there, but it is applied uniformly with no regard for the variance of the position in which `T` occurred. When `T` occurs under a mutable container head (`list`/`set`/`dict`, which `generic_param_variance` correctly classifies `Invariant`), widening is unsound: the callee body writes elements of the widened union into a container the caller still believes is `list[int]`.

**Impact.** The invariance of `list`/`set`/`dict` — which the checker enforces correctly for direct assignment (`let xs: list[Animal] = dogs` is rejected) — is bypassed entirely whenever the container flows through a generic function. Any `def f[T](a: list[T], b: list[T])`, `def merge[K, V](a: dict[K, V], b: dict[K, V])`, or similar signature (the single most common generic-function shape in real code) silently accepts mismatched containers and lets the callee corrupt the caller's collection. The corruption is delayed and reported far from the call site, which is the hardest class of type error to debug.

**Suggested fix.** After the existing forward/backward inference in the call arm (the `bind_typevars_and_substitute_bidirectional` / `_hkt` result at ~15668-15678), add a conservative post-substitution re-validation pass: for each positional/keyword argument whose declared formal mentions a TypeVar that occurs at an **invariant** position (walk the formal with `generic_param_variance` / `user_generic_param_variance`, i.e. under a `list`/`set`/`dict`/mutable head or a user generic inferred `Invariant`), re-check the actual against the *substituted* formal and emit `type_mismatch` on failure. Gate it hard for additive compatibility: skip when the substituted formal still contains a free TypeVar (`contains_free_typevar`), when any actual is `Unknown`/`Any`, inside `unsafe:`, and for HKT constructor variables — so the existing documented scalar union-widening (`pair(1, "two")`) and every currently-green corpus program are unaffected. Alternatively (narrower) make `bind_typevars_checked` refuse to union-widen when the binding site is invariant and report a mismatch there instead.

### F46 — [HIGH] Inline `?` in a `while` condition is hoisted out of the loop, so the fallible expression is evaluated once and the loop condition is frozen — wrong result or infinite loop

**Category:** emit-runtime-crash · **Domain:** types-result · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-syntax/src/preprocess.rs:6055`

**Mechanism.** Same pass as the `elif` finding: `rewrite_inline_question_ops_one_line` (preprocess.rs:6022) emits `TMP = call` / `if isinstance(TMP, __typhon_Err__): return TMP` at preprocess.rs:6055-6057 immediately *above* the physical line carrying the `?`, then rewrites the operand in place to `TMP.value`. When the line is `while COND:`, the fallible call is evaluated exactly once, before the loop, and every iteration re-reads the cached `TMP.value`. Python's `while` re-evaluates its condition each iteration, so the lowering changes the *evaluation count* of the operand from N to 1. Any condition whose truth depends on the fallible call's changing value therefore either never terminates or terminates on the wrong iteration; any side effect inside the callee runs once instead of N times. **Impact.** A `Result`-returning drain/poll/retry loop (`while read_next()? != SENTINEL:`) compiles to an infinite loop or a loop with the wrong trip count, with a clean `tyc check` and syntactically valid Python. Because the emitted code is valid, the only symptom is a hang or wrong output in production.

**Suggested fix.** Refuse to lift out of a `while` header, and lower it correctly instead — rewrite `while COND_WITH_Q:` into `while True:` with the lifted `TMP = call` / `if isinstance(TMP, Err): return TMP` statements at the top of the body followed by `if not COND': break`. If the correct lowering is too invasive for a point release, take the conservative route and reject the shape with a targeted `tyc::invalid_question_op` (additive: it only rejects programs that already miscompile), directing the author to bind the call inside the loop body.

This is purely a VM-internal correctness fix — no language surface, no diagnostic, so it is additive by construction.

A record sort whose tiebreak field is a bytes column silently loses its secondary ordering. Separately, a genuine type error (sorting a heterogeneous list, a common bug in untyped boundary data) is masked into a plausible-looking result instead of the `TypeError` CPython raises, so the VM hides the very defect the developer was about to find. Because the failure is order-preserving it looks correct on already-sorted input and only manifests on real data.

**Suggested fix.** Make the incomparable case an error rather than a fallback. Change `value_cmp` (interp.rs:1962) to `match a.py_cmp(b) { Some(o) => Ok(o), None => Err(type_error(format!("'<' not supported between instances of '{}' and '{}'", a.type_name(), b.type_name()))) }` — the `sorted` native's existing `sort_error` capture then surfaces it correctly, and `min`/`max` propagate it via `?`. The depth-guard `None` (value.rs:1406) should be distinguished from a missing-arm `None` so a deep-but-comparable structure raises `RecursionError` rather than a bogus TypeError. Pair this with finding #5 (adding the missing `py_cmp_inner` arms) so the change turns wrong answers into correct answers rather than into new exceptions. This is VM-internal; no language surface changes, and it can only convert silent-wrong output into either a correct result or the same exception CPython raises.

### F52 — [HIGH] VM isinstance(True, int) is False and isinstance(x, object) is False - is_instance_of lacks the bool-subtype-of-int and object arms, silently changing control flow

**Category:** vm-parity · **Domain:** vm-stdlib · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-vm/src/builtins.rs:1407`

**Mechanism.** pub(crate) fn is_instance_of(val: &Value, cls: &Value) (builtins.rs:1393) resolves the class argument to a name and matches (name, val) pairs. ### F53 — [MEDIUM] auto-parallel-reductions loses all partial accumulation when the element expression raises, and the module doc's exception-preservation claim is wrong

**Category:** soundness · **Domain:** analyse-perf · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-analyse/src/reductions.rs:320`

**Mechanism.** build_reduction_stmt (reductions.rs:320) lowers 'for x in ITER: ACC += EXPR' to the single statement 'ACC += sum(map_pure(lambda x: EXPR, ITER))'. In the sequential loop ACC is updated once per element, so if EXPR raises on element k the accumulator already holds the sum of elements 0..k-1 when the exception unwinds. In the rewritten form the entire sum(map_pure(...)) right-hand side must evaluate before the += store happens, so a raise anywhere in the map leaves ACC at its pre-loop value. Any try/except around the loop, the only way to observe this, therefore sees a different accumulator. The module doc at reductions.rs:44-50 explicitly reasons about exceptions and concludes that map_pure returns results in input order so the first raising element still propagates first; that covers WHICH exception propagates but not the STATE left behind. Condition 4's purity requirement (is_pure_value_expr, parallel.rs:573) admits raising expressions: integer // and % and calls to @pure functions all raise while being side-effect-free, so purity is not a proxy for non-raising. The same divergence also splits tyc run (the VM does not apply the rewrite) from tyc build plus CPython, breaking the VM drop-in invariant.

**Impact.** Silent wrong answers, the worst failure mode, because nothing crashes. Any accumulate-with-recovery idiom (summing parsed values while tolerating a bad record, integrating with a divide-by-zero guard, accumulating scores where one entry violates a @pure helper's precondition) returns a structurally plausible but wrong result once the knob is enabled. It also makes tyc run and tyc build plus python disagree on the same source, which the project treats as a bug class in its own right.

**Suggested fix.** Either (a) give the reduction path its own stricter non-raising predicate rather than reusing is_pure_value_expr, which is shared with the comprehension rewrite where partial-state divergence cannot arise, admitting only literals, plus/minus/times over the target and captured ints, and calls attested non-raising; or (b) refuse the rewrite whenever the loop is lexically inside a try block in the same function, which is cheap and covers every case where the divergence is observable. Both are narrowings of an opt-in transform. The reductions.rs module doc's exception paragraph must be corrected either way, since it asserts a preservation property the lowering does not have.

### F65 — [MEDIUM] `global` / `nonlocal` silently defeats `let` immutability — a `let`/`freeze let` binding can be reassigned from another scope with no diagnostic

**Category:** soundness · **Domain:** resolve · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-resolve/src/lib.rs:1736`

**Mechanism.** `declare_target` (lib.rs:1736) handles a bareword assignment by looking up the name with `r.lookup_local(scope, ...)` — a **scope-local** lookup that deliberately does not walk the parent chain. For `global CONFIG; CONFIG = "b"` inside a function, the function scope has no `CONFIG` binding, so `existing_mut` is `None`. The `declared_global_or_nonlocal` guard at lib.rs:1762 then suppresses `tyc::missing_binding_kind`, and the mutability fallback at lib.rs:1868-1873 computes `existing_mut.unwrap_or(if default_val { Let } else { Mut })` — `default_val` is `false` for a function scope, so the assignment declares a **brand-new `Mutability::Mut` binding in the function scope**. The module-level `let CONFIG` binding is never consulted, so `declare_full`'s `existing.mutability == Mutability::Let` check (lib.rs:1085) can never fire. `global_nonlocal_names` is used only to *suppress* the missing-binding-kind error; it is never used to redirect the write to the binding it actually names. The identical path applies to `nonlocal` against an enclosing function's `let`. Note tyc-types disagrees with tyc-resolve here: it *does* model the write as hitting the module binding (it type-checks the assigned value against the global's declared type) and its help text calls the binding `mut` — so resolve and types hold contradictory views of the same binding's mutability.

**Impact.** The headline guarantee of `let` ("immutable binding; reassignment is `tyc::immutable_assign`") has a two-keyword escape hatch that fires no diagnostic at all. Any `let`/`freeze let` module constant or captured local can be rebound from anywhere in the program, so readers and the checker can no longer rely on a `let` being single-assignment. `freeze let` is the worst case: `deep_freeze` protects the *value*, and `let` was supposed to protect the *binding* — `global CFG; CFG = {...}` defeats both at once with a clean build. It also silently corrupts the resolver's binding graph (an extra phantom function-scope binding), which feeds LSP go-to-definition and the unused-import pass.

**Suggested fix.** In `declare_target`, when `declared_global_or_nonlocal` is true, resolve the name through the parent scope chain (module scope for `global`, nearest enclosing *function* scope for `nonlocal`) instead of declaring a fresh local. If the resolved binding's `mutability == Mutability::Let`, emit `tyc::immutable_assign` anchored at the outer declaration, exactly as the in-scope path does; if it is `Mut`, record the write against that binding rather than pushing a new one. This is additive on correct programs: a program that mutates a `let` through `global`/`nonlocal` was already violating the documented rule, and code that declares `mut COUNTER: int = 0` at module level (the working `t1.ty` idiom) is unaffected. Keep the `missing_binding_kind` suppression as-is.

**Category:** performance · **Domain:** tests-ci · **Verifier verdict:** CONFIRMED · **Site:** `scripts/perf-gate.sh:49`

**Mechanism.** `scripts/perf-gate.sh:49` pins the benchmark corpus to `examples/47-mini-app` and line 54 times `tyc build <corpus> --no-sync --check`. That project's `typhon.toml` declares four `[dependencies]` (fastapi, uvicorn, pydantic, anthropic) and ships no `.venv`. `tyc-venv::discover_python` (tyc/crates/tyc-venv/src/lib.rs:301) probes `.venv/bin/python` and `.venv\Scripts\python.exe`, finds neither, and falls back to `which_python3()` (line 326/341), so `introspect_batch_via_python` (line 544) spawns a real CPython interpreter to introspect four packages that are not installed. That subprocess spawn + interpreter startup dominates the measurement.

The gate compares the *total* wall-clock median against `perf-baseline.json` `median_ms: 89` with `threshold: 0.20`, i.e. it fails above 106.8 ms. Because roughly 53 ms of the ~90 ms median is the Python subprocess and only ~37 ms is the compiler pipeline (including ~4.7 ms of `tyc` process startup, measured separately), a genuine compiler regression must be ~45% before the gate trips — more than double the advertised 20%. The same coupling makes the number sensitive to the runner's Python startup time: a `ubuntu-latest` image bump that changes CPython's import cost moves the measurement with no compiler change at all, which can either consume the headroom (spurious FAIL) or shift the baseline upward and mask a real regression. My two independent 9-run medians on an unchanged binary differed by 6.7% (96.3 ms then 90.2 ms) — a third of the gate's entire headroom is run-to-run noise sourced from the subprocess. The corpus is also small (5 `.ty` files, 356 lines total), so passes with super-linear complexity in file count or nesting depth are under-represented.

**Impact.** The perf-gate job — one of CI's three gates, and the only defence against algorithmic blowups like the O(2^depth) assignability and O(N²) source-map regressions the project has already shipped and fixed — is roughly half as sensitive as `docs/performance-baseline.md` and `perf-baseline.json` claim. A 40% slowdown in the type checker passes the gate. Conversely the gate is exposed to spurious failures from runner-image Python changes that have nothing to do with the compiler, which trains maintainers to refresh the baseline reflexively.

**Suggested fix.** Set `TYC_NO_INTROSPECT=1` in `BUILD_FLAGS`' environment inside `scripts/perf-gate.sh` (the kill-switch already exists, added in alpha.3) and re-record the baseline with `--update` so the gate measures compiler work rather than CPython startup; the threshold then means what the docs say it means. Optionally widen the corpus to include a second, larger project (e.g. one of `examples/apps/`) as a separate timed entry so per-file and per-depth scaling are both represented. Both are CI-side changes with no effect on the language or compiler.

### F70 — [MEDIUM] `class!` synthesised `__init__` treats a `ClassVar[T]` field as a constructor parameter and strips its class-level default — the class attribute ceases to exist, AttributeError on a clean check

**Category:** emit-runtime-crash · **Domain:** types-classes · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-desugar/src/lib.rs:3163`

**Mechanism.** `synthesise_raw_class_init` (tyc-desugar/src/lib.rs:3159) collects `raw_fields` from every top-level `Stmt::AnnAssign` with a bare `Name` target (:3163-3181) with **no `ClassVar` filter**. `tyc-types::collect_class_shape` (:8717-8727) does the opposite — it explicitly `continue`s on `is_classvar_annotation`, precisely so ClassVars stay out of the constructor surface (the fix for audit item [45]). The two sides therefore disagree on the parameter list: the checker's `field_order` is `[y]` while the emitted `__init__` is `(self, y, KIND="m")`. Worse, the `class!` contract strips class-level field defaults from the body when an `__init__` is synthesised (so a PyTorch-style default isn't evaluated twice), which converts the `ClassVar` from a *class* attribute into a per-instance attribute assigned in `__init__`. The documented and intended read `M.KIND` then resolves against nothing. As a bonus, the emitted parameter annotation `KIND: ClassVar[str]` is invalid typing (PEP 526 forbids `ClassVar` outside a class body), so an external `[checker] external = "ty"` pass would also reject the artifact. This is distinct from audit item [45], which fixed only the *checker*'s kwarg surface and never touched the desugar-side synthesiser.

**Impact.** `class!` is the prescribed form for subclassing a framework base (torch.nn.Module, custom exceptions), and `ClassVar` is the prescribed way to declare class-level constants on such a class — the `tyc::class_attr_shadows_slot` help text actively tells users to "annotate each field as `ClassVar[T]`". Combining the two produces a program that checks clean on every surface and then raises `AttributeError` the first time the class constant is read. It also silently reshapes the constructor (an extra trailing keyword parameter the checker will report as `unknown_kwarg` if the user passes it), and the ClassVar-before-required-field ordering bypasses `tyc::field_default_ordering` entirely because the checker's field list excludes the ClassVar.

**Suggested fix.** In `synthesise_raw_class_init` (tyc-desugar/src/lib.rs:3163-3181), skip any `AnnAssign` whose annotation is `ClassVar[...]`/bare `ClassVar` — reuse the same predicate `tyc-types::is_classvar_annotation` implements (or lift it into a shared helper so the two crates cannot drift again), and leave the ClassVar statement — *including its `= default` value* — untouched in the class body so it remains a real class attribute. Purely additive: it only makes `class!` classes carrying a `ClassVar` construct and read the way the checker already models them; no currently-working program changes shape (a `class!` without a `ClassVar` emits byte-identically).

### F71 — [LOW] tyc build writes every artifact with non-atomic std::fs::write; an interrupted build leaves a persistent 0-byte build/main.py that CPython runs successfully with exit 0

**Category:** crash-panic · **Domain:** cli-build · **Verifier verdict:** PARTIAL · **Site:** `tyc/crates/tyc/src/commands/build.rs:1130`

**Mechanism.** In build::run, each emitted module is written with std::fs::write(&out_file, &python_src) (build.rs:1130); the .py.map sidecar (build.rs:1171), the .pyi stubs (build.rs:1335) and the generated typhon_runtime/*.py (build.rs:1377) use the same call. std::fs::write opens with O_TRUNC and then writes, so the target is observably empty (or half-written) for the whole duration of the write, and if the process dies inside that window the truncated file is what remains on disk. There is no temp-file plus rename, no fsync, and no post-write verification. This is doubly wrong because the project already solved exactly this hazard elsewhere: tyc-format::atomic_write (tyc/crates/tyc-format/src/lib.rs:1232) was added in v1.0.0-alpha.3 with the comment 'A crash, disk-full ... readers see either the old or the new content, never a half-written file', and tyc fmt routes through it. tyc build, which produces the artifact people actually ship and execute, does not. The failure is silent rather than loud because a 0-byte file is valid Python: python build/main.py on a truncated entry point compiles, runs, prints nothing and exits 0, so a CI packaging step or a downstream runner sees success.

**Impact.** A build interrupted by Ctrl-C, an OOM kill, a CI job timeout, a full disk or a container stop leaves a truncated or empty .py in build/. Because an empty Python file executes successfully and exits 0, the failure is silent: a packaged artifact, a container image layer, or a tyc run --compile invocation reports success while doing nothing. Concurrent readers (a watch-mode server, a second tyc invocation, a running python build/main.py) can also observe an empty or half-written module. The next tyc build does overwrite the damage, but nothing detects it in the meantime.

**Suggested fix.** Hoist tyc-format's atomic_write into a shared helper (it already resolves symlinks, sync_all's, and preserves the mode bit) and route every artifact write in build::run through it: the emitted .py (build.rs:1130), the .py.map (build.rs:1171), the .pyi (build.rs:1335), and each typhon_runtime/*.py (build.rs:1377). Purely additive, no language or diagnostic surface change. Optionally add a per-build lock file in the output dir so two concurrent tyc build invocations against the same out serialise rather than interleave.

### F72 — [LOW] Additive-compatibility violation shipped in alpha.2: the new subscript-assignment check rejects an `object`-typed RHS, breaking a stress fixture that previously checked clean and ran correctly

**Category:** false-positive · **Domain:** corpus · **Verifier verdict:** PARTIAL · **Site:** `tyc/crates/tyc-types/src/lib.rs:10327`

**Mechanism.** `check_stmt` (tyc-types/src/lib.rs:10045), `Stmt::Assign` handler, `Expr::Subscript(sub)` branch at line 10327 — the v1.0.0-alpha.2 "subscript assignments are checked" work (CHANGELOG.md:498). For a `dict[K, V]` receiver it runs `if !c.is_assignable(&val_ty, &value_type) { c.mismatch(...) }` (line 10358-10360) with no leniency carve-out. `object` is a *declared* top type, not `Unknown`, so `is_assignable(int, object)` is false and the diagnostic fires. Every other conservative check added in the same release degrades on absent evidence; this one does not distinguish "the RHS is provably wrong" from "the RHS is the top type and therefore carries no evidence either way". The canonical Python `__setattr__(self, name, value)` override has no correct narrower annotation than `object`, so the pattern is now unwritable. The project's hard constraint is that a new diagnostic may fire only on code that already failed at runtime; this program's recorded baseline is `check=0 vm=0 comp=0 [PASS]`.

**Impact.** A previously-accepted, previously-correct program is now rejected — the exact defect class the project names as its worst case. Concretely it makes descriptor-style `__setattr__` / `__getattr__` overrides on a `plain class` (the form Typhon documents for metaclass-driven and ORM-style libraries) impossible to write, since Python's protocol mandates an `object`-typed value parameter. More broadly, any write of an `object`-typed value into a `dict[K, V]` or `list[T]` now errors with no narrowing path short of an `isinstance` ladder or an `as!`.

**Suggested fix.** At lib.rs:10327, suppress the mismatch when the RHS type is exactly `object` (and when it is `Unknown`/`Any`, if not already), matching how the release's other conservative checks degrade on no-evidence types. If the write genuinely warrants a nudge, demote it to an advice-level lint rather than an error so it cannot break a build. Regression-test with `stress/round-2026-06-21/repros/106-getattr-fallback.ty` and promote that fixture into the gated corpus.

### F73 — [LOW] tyc-types::infer_expr_ctx recurses with no depth guard — a large machine-generated expression aborts the compiler with a stack overflow instead of emitting a diagnostic

**Category:** crash-panic · **Domain:** robustness · **Verifier verdict:** CONFIRMED · **Site:** `tyc/crates/tyc-types/src/lib.rs:14665`

**Mechanism.** `infer_expr_ctx` (crates/tyc-types/src/lib.rs:14665) is a single very large `match` over `Expr` that recurses structurally into every sub-expression, with no depth parameter and no budget. The only mitigation anywhere in the pipeline is the fixed worker stack: `WORKER_STACK_SIZE: usize = 256 * 1024 * 1024` (crates/tyc/src/main.rs:20), mirrored for the LSP blocking pool at crates/tyc-lsp/src/lib.rs:2525. Because the function is monolithic, its stack frame is large (measured ~3.2 KiB/level: 256 MiB / ~80,000 levels), so the 256 MiB budget buys far fewer levels than its size suggests.

A left-associative `a+a+a+...` chain produces a left-deep `BinOp` tree of the same depth as the term count, so the term count is the recursion depth. The vendored Ruff parser handles the same input fine — only the type checker overflows — so this is not a parser limitation the input "deserves".

Secondary observation from the same sweep: `infer_expr_ctx` is also quadratic in nesting depth for some shapes (nested calls `f(f(...f(1)...))`: n=2000 0.11s, 4000 0.37s, 8000 1.36s, 16000 5.39s; nested attribute chains `a.b.b.b…`: n=2000 0.4s, n=10000 11.6s), so a file large enough to threaten the stack limit is already very slow.

**Impact.** `tyc` aborts the process rather than reporting a diagnostic on an input it is expected to reject or accept gracefully. Hand-written code will not hit 80,000 terms, but generated code plausibly can: a lookup table built as a chained expression, a `tyc migrate` of a machine-generated Python module, or a code generator emitting a long sum/concatenation. The user sees `fatal runtime error: stack overflow` with no file name, no line, and exit 134 — indistinguishable from a compiler bug of any other kind. In the LSP the same recursion runs on the blocking pool, so an editor buffer containing such an expression kills the language server for the entire workspace. The project's stated bar ("a compiler must never panic or hang on any input") is not met by relying solely on a fixed stack size.

**Suggested fix.** Thread a depth counter through `infer_expr_ctx` (and the corresponding statement walker) and, on exceeding a generous budget (e.g. 2,000 — well past any plausible real program and ~1/40th of the current empirical limit), return `Type::Unknown` and push a dedicated `tyc::expression_too_deep` diagnostic anchored at the expression's span. Returning `Unknown` keeps the result permissive so no currently-accepted program is newly rejected; the new diagnostic fires only on input that previously aborted the process, which satisfies the additive-compatibility rule. A cheaper interim mitigation is a reusable `stacker::maybe_grow`-style guard at the head of `infer_expr_ctx`, but the explicit budget is preferable because it also bounds the quadratic time cost observed for nested-call and nested-attribute chains.

### F74 — [LOW] `tyc::contains_secret_literal` misses first-tier secret name shapes (PASSPHRASE, CREDENTIALS, DSN, COOKIE, AUTHORIZATION, WEBHOOK), and the PASS boundary rule that excludes PASSPORT also excludes PASSPHRASE

**Category:** diagnostics · **Domain:** security · **Verifier verdict:** PARTIAL · **Site:** `tyc/crates/tyc-analyse/src/lib.rs:3544`

**Mechanism.** `SECRET_NAME_KEYWORDS` (tyc-analyse/src/lib.rs:3544) is the single shared table behind both the lint and the `tyc build` scan, containing only PASSWORD/SECRET/TOKEN/KEY/PWD/PASS and their API_* variants. `is_secret_name` (:3567) additionally requires each match to be bounded by string start/end, an underscore, or a camelCase transition — the rule that stops `MONKEY` matching `KEY` and `PASSPORT` matching `PASS`. That same rule silently disqualifies `PASSPHRASE`: `PASS` matches at index 0 with `start_ok`, but `end_ok` requires `upper[4] == b'_'` or a lower→upper transition, and in an all-caps constant `name[3]` is `S` (uppercase), so `end_ok` is false and the name never fires. Several other canonical secret-bearing names have no keyword in the table at all: `CREDENTIALS`, `DATABASE_DSN`, `SESSION_COOKIE`, `AUTHORIZATION`, `SLACK_WEBHOOK_URL`, `SIGNING_CERT`. Separately, the doc comment on `is_secret_name` (:3560-3566) says the function matches names that "end with" a recognised suffix, while the implementation does a bounded substring scan anywhere in the name — minor doc drift against the actual behaviour.

**Impact.** A warn-level heuristic that SECURITY.md already calls "best-effort … not a guarantee", so the ceiling is low — but the misses are not exotic. `PASSPHRASE` is arguably the single most secret-shaped English word after `PASSWORD`, and a hardcoded `DATABASE_DSN` or `SLACK_WEBHOOK_URL` is a routine real-world credential leak. A user who sees the lint fire on `API_TOKEN` reasonably infers it covers this class, so the gaps produce false assurance rather than simple silence.

**Suggested fix.** Add `PASSPHRASE` ahead of `PASS` in `SECRET_NAME_KEYWORDS` (the table's documented longest-first invariant handles the ordering), plus `CREDENTIAL`, `CREDENTIALS`, `AUTHORIZATION`, `WEBHOOK`, `COOKIE`, `DSN`, and optionally `PRIVKEY`/`SIGNING`. Because the two consumers already share the one table, no drift risk is introduced. Severity stays `warn`, so this is additive: it can only add warnings on code that was already leaking a literal, never reject a previously-correct program. Also correct the `is_secret_name` doc comment (:3560) to say the match is a bounded substring scan, not a suffix test.
