A full review of the `v1.0.0-alpha.6` tree against the shipped compiler:
what actually works, where the docs and the bundled skill disagree with the
binary, and what the example corpus really guarantees.

Everything below was verified by running `tyc` — no claim here is taken from a
document. Reproductions are given so each finding can be re-checked.

## 3. Compiler findings

### C1 — a forgotten `await` inside an `async def` is completely silent (soundness)

**The most serious finding.** `tyc::missing_await` fires only when the caller is
*synchronous*. A forgotten `await` inside another `async def` — by far the
likelier mistake, since that is where await-heavy code lives — produces no
diagnostic at all. No `tyc::type_mismatch` fires either: the checker types the
call by its return type regardless of whether it was awaited, so a coroutine
object flows into a concretely-typed slot unchallenged.

```python
async def fetch_a() -> dict[str, int]:
    await asyncio.sleep(0)
    return {"a": 1}

async def run() -> int:
    let b: int = await fetch_b()          # some other await, so
    let d: dict[str, int] = fetch_a()     # `async_without_await` stays quiet too
    return len(d) + b
```

`tyc check` reports **nothing**. The emitted Python dies with
`TypeError: object of type 'coroutine' has no len()` plus
`RuntimeWarning: coroutine 'fetch_a' was never awaited`.

`tyc::async_without_await` sometimes covers for this by accident — if the
caller has *no* awaits it warns about that instead — which is probably why the
gap survived.

This is squarely in the category `CLAUDE.md` permits narrowing for: the
programs it would newly reject already crash at runtime. Any fix must keep the
deliberate-deferral pattern legal:

```python
let task = fetch_a()      # bind now …
let data = await task     # … await later
```

so the narrow rule is "an un-awaited async call whose result flows into a slot
annotated with the coroutine's *return* type", not "any un-awaited async call".

Reproduction: `examples/errors/12-known-gaps/missing_await_in_async_caller.ty`.

### C2 — `tyc::implicit_any` does not cover function signatures

It fires on annotated-assignment positions only — locals, module bindings, and
class fields. Function **parameter** and **return** annotations are not checked:

```python
let xs: list = [1, 2, 3]        # ✅ error
def keys(d: dict) -> list:      # ❌ accepted silently
    return list(d.keys())
```

The signature position is the higher-leverage one — it widens every call site
*and* the whole body. Both `docs/diagnostics/implicit_any.md` and the skill
used a function signature as their worked example, i.e. documented exactly the
case that does not fire (fixed; see D3).

Closing this would reject programs that run correctly, so it is a deliberate
narrowing decision rather than a bug fix. **Corpus impact measured: zero** — no
file in `examples/` or `stress/` has a bare collection in a signature, so it
could land without touching the corpus.

Reproduction: `examples/errors/12-known-gaps/bare_collection_in_signature.ty`.

### C3 — `tyc::missing_initialiser` is dead code

The variant and constructor exist in `tyc-diagnostics` and the code is listed
by `tyc explain --list`, but **nothing in the compiler calls
`TycError::missing_initialiser`** — verified by searching every call site in
`tyc/crates/`. It can never fire.

Its doc page still described pre-v0.7.0 behaviour ("the Rust-style
declare-then-assign shape is not supported"), which v0.7.0's
definite-assignment analysis replaced — the page's own example now compiles
cleanly. A declare-only `let` that is never assigned *and* never read is
accepted silently; reading one on an unassigned path is caught by
`tyc::use_of_uninitialised`, and a second assignment by
`tyc::immutable_assign`.

Decision needed: wire it up as a dead-binding lint, or retire the code. Docs
now describe the current reality either way.

Reproduction: `examples/errors/12-known-gaps/unassigned_declare_only_let.ty`.

### C4 — `tyc::contains_secret_literal` never fires under `tyc check`

The secret-shaped-name lint is emitted from `tyc/src/commands/build.rs`, so it
only appears during `tyc build`. `docs/cli.md` and the skill both recommend
`tyc check src/` as the CI primary gate — a pipeline that follows that advice
will never see this warning, and a resolved API key inlined into the build
artifact ships unflagged.

Worth either moving the scan into the check path or adding a note to the CI
recommendation. Documented in the corpus meanwhile.

Reproduction: `examples/errors/10-footguns-and-lints/contains_secret_literal.ty`
(carries a `# REQUIRES: build` directive for exactly this reason).

### C5 — three raw-source validators mask every other diagnostic in the file

`tyc::invalid_question_op`, `tyc::lazy_usage` and `tyc::extend_builtin` are
produced by validators that run on raw text before preprocessing, and
`check_source_file_with_imports` returns immediately if any of them errors
(`tyc-db/src/lib.rs`). One misplaced `?` therefore hides every type error in
the file:

```python
def bad() -> str:
    let n: int = f()?        # tyc::invalid_question_op — the only code reported
def unrelated() -> int:
    let s: str = "hello"
    return s                 # tyc::type_mismatch — never surfaces
```

Measured on a realistic file: 1 diagnostic reported where 10 exist across 7
codes. This is structurally necessary (those three forms are *text rewrites*,
so a malformed one leaves nothing to parse) and not obviously worth changing —
but it is surprising enough to be worth documenting, since it turns one fix
into several fix-recheck cycles.

Documented in `examples/errors/11-multi-error-programs/error_masking.ty`.

### C6 — `tyc install skill` silently dropped a file *(fixed)*

`references/21-rescue-boundaries.ty` existed in `tyc/crates/tyc/skill/` and was
indexed by the skill's own `references/README.md`, but was missing from the
`SKILL_FILES` manifest — so every project that ran `tyc install skill` got 20
reference programs and an index promising 21.

Fixed, plus a `manifest_covers_every_file_in_the_skill_source_tree` test so the
hand-maintained manifest can't drift again, and the "20 example programs"
summary line is now derived from the manifest.

### C7 — two warn-level diagnostics rendered with the error glyph *(fixed)*

`tyc::method_in_class_body` and `tyc::typing_alias_deprecated` were counted and
grouped as warnings but drew miette's `×` rather than `⚠`, because their
declarations omitted `severity(Warning)`. Every other warn-level code in the
catalog declares it. Cosmetic, but a warning that looks like an error costs
someone a debugging detour. Fixed.

### C8 — `tyc explain --list` advertised two codes that don't exist *(fixed)*

`freeze` and `pub` are language-reference topics with pages under
`docs/diagnostics/`; they were printed as `tyc::freeze` / `tyc::pub` alongside
the 87 real codes, so anyone reading the list would expect them in build
output. They are now labelled `(topic, not a diagnostic code)`.

## 3b. Differential gap hunt — 26 probes, 11 new findings

Section 3's findings came from reading. This round came from *running*: a
battery of diverse probe programs, each pushed through three paths — `tyc
check`, `tyc run` (VM), and `tyc build` + CPython 3.13 — with the last two
diffed against each other. `docs/vm.md` says the VM "must stay a drop-in for
`tyc build && python` — VM/CPython divergences are bugs", which makes that diff
a mechanical bug detector.

Areas probed: integer/float semantics, string and bytes methods, container
operations and slicing, exception hierarchies with `else`/`finally`, generators
and the iterator protocol, dunder-heavy classes, pattern matching, closures and
scoping, PEP 695 generics, `Result` plumbing, `as!`, decorators, enums/models/
`freeze let`/`newtype`/`comptime`, interfaces and `extend`, operator precedence
through lowering, format specs, recursion, comprehension corners, async
concurrency, and deliberate soundness attacks.

**Verified sound** — two attacks the checker correctly repelled: flow narrowing
of an instance field invalidated by an intervening mutating call
(`tyc::operator_type_mismatch` on the widened type), and writing a
`list[Animal]` alias of a `list[Dog]` (`tyc::type_mismatch`, invariance held).

### Type-checker false positives — valid code rejected

**F1 — `try`/`except`/`else` where the `else` returns.** The `else:` arm's
return is not counted by reachability analysis, so a function that returns on
every path draws `tyc::missing_return`. Narrow and reproducible: `try`/`except`
and `try`/`except`/`finally` are both accepted; only the `else:` form trips it.
The `else:` clause is the idiomatic place for the success path, so this hits
ordinary code.
→ `examples/errors/13-false-positives/try_else_missing_return.ty`

**F2 — `case {}:` is treated as refutable.** An empty mapping pattern places no
constraints on the subject, so it matches *any* mapping — it is the mapping
form of `case _:`, not a test for an empty dict (verified against CPython
3.13). The checker does not count it, so an exhaustive `match` draws
`tyc::missing_return`. `case _:` in the same position is accepted.
→ `examples/errors/13-false-positives/empty_mapping_pattern.ty`

### Soundness — invalid code accepted

**S1 — a variable index into a fixed-arity tuple type-checks as any element
type. *(fixed)*** Given `t: tuple[int, str]` and a non-constant `i`, both `let
a: int = t[i]` and `let b: str = t[i]` were accepted — the same expression
satisfying two incompatible annotations, because the read degraded to `Unknown`
rather than to the union `int | str`. A *constant* index was checked correctly,
and homogeneous containers were fine; it was specifically this read position.
Runtime result: `TypeError: can only concatenate str (not "int") to str`.
v1.0.0-alpha.2's newly-typed-positions sweep covered slice reads and subscript
*assignments*; this read was missed.

The subscript arm of `infer_expr_ctx` (`tyc-types/src/lib.rs`) resolved a
fixed-arity tuple read only when `const_int_index` returned a literal, and fell
through to `Unknown` otherwise. It now returns `Type::union_of(elts)` for a
non-constant index, so `t[i]` is `int | str` everywhere the read is typed
(`let` initialiser, call argument, `return`, comprehension). A homogeneous
`tuple[int, int]` collapses back to `int` through `union_of`, and variadic
`tuple[T, ...]` is a different head (`tuple_variadic`) that was already typed
correctly. The reproduction moved to
`examples/errors/02-types-and-annotations/tuple_variable_index.ty` with an
`EXPECT-ERROR: tyc::type_mismatch` header.

### VM ↔ CPython divergences

Each of these builds and runs correctly through `tyc build` + CPython, and
misbehaves under `tyc run`.

**V1 — inline `?` did not parse in the VM. *(fixed)*** The VM handled `?` only
in statement-tail position. `return Ok(p(a)?)`, `let x: int = p(a)? + 1` and
`if p(a)? > 0:` were all hard parse errors under `tyc run`, while `tyc check`
and `tyc build` accepted every one. Inline `?` is a documented, shipped feature
— the skill's §9 gives `Ok(add(parse(s)?, parse(t)?))` as its worked example —
so this was the widest-blast-radius divergence found: any `Result`-heavy
program written to the documented surface hit it.

Root cause was a one-pass omission in the VM's preprocessing pipeline. The
build path (`tyc-db`) runs

```rust
expand_question_ops(&expand_inline_question_ops(&expand_pipes(…)))
```

while `tyc-vm/src/lib.rs` ran the same chain **without
`expand_inline_question_ops`**, at both of its two call sites — so only the
end-of-line `?` the outer pass handles ever got lowered. Adding the missing
pass fixes every shape above. The reproduction is now a passing parity case
(`examples/parity/inline_question_op.ty`) covering all five shapes.

**V2 — `max()` picks the wrong element on a tie.** CPython's `max` returns the
*first* maximal element and never replaces on a tie; the VM returns the last.
`min` is correct. Silent wrong output, and ties are common in exactly the
"highest score wins" shape where a user `__lt__` gets written. v0.12.0 fixed
`sorted`/`min`/`max` to dispatch a user `__lt__` at all; tie order was not
covered.

**V3 — `lambda x=x:` is unimplemented in the VM.** `TypeError: <lambda>()
missing required argument`. Default arguments on a `def` work. **This is the
fix `tyc` itself prescribes** — `tyc explain loop_closure_capture` tells the
user to write `lambda i=i: i`, which then crashes under `tyc run`.

**V4 — the string precision spec is ignored.** For a string operand, `.N` in a
format spec is a maximum length, so `f"{'hi':.1}"` is `'h'`. The VM applies
precision to numerics only and passes strings through whole. Every other spec
probed (fill, align, sign, width, grouping, `#`, base conversions, `%`, `=`,
`!r`, nested `{width}`/`{precision}`) agrees.

**V5 — frozen mappings print as their repr.** `freeze let` lowers nested dicts
to `MappingProxyType`, whose `__str__` delegates to the underlying dict
(`{'k': (1, 2)}`) while `__repr__` is `mappingproxy({'k': (1, 2)})`. The VM
uses the repr form for both, so printing a config differs between `tyc run` and
the shipped build. Immutability itself is correct on both paths.

**V6 — four missing stdlib members**: `str.isascii()`, `str.isprintable()`,
`bytes.count()`, and `datetime.timezone`. Each sits next to an implemented
neighbour (`str.isdigit`, `bytes.find`, `datetime.now`), and `timezone.utc` is
what every UTC-aware timestamp needs.

→ all six: `examples/parity/divergent/`

## 3c. The parity corpus

The probes that *passed* are as valuable as the ones that failed, so the
12 clean ones are checked in as `examples/parity/` with a harness
(`tyc/crates/tyc/tests/parity_corpus.rs`) asserting byte-identical stdout
between the two execution paths. `examples/parity/divergent/` holds the six
confirmed divergences under the inverse assertion — they must *keep* differing,
so fixing one fails the test as a prompt to promote the file.

This turns the VM's drop-in guarantee from a documented intention into a
CI-enforced property. Combined cost: ~3s.

## 5. Test-coverage gaps closed

`CLAUDE.md` calls the example corpus "the regression net". It was partly
enforced: `pipeline.rs::corpus_examples_all_check_clean` sweeps every `.ty`
under `examples/` as a *standalone file* and asserts the exit status. Three
things it did not cover, now added in `tests/example_corpus.rs`:

1. **The 16 multi-file projects** (`examples/apps/*`, `47-mini-app`) were never
   checked as projects — only their files individually, which does not exercise
   cross-module resolution, `pub *` aggregation, or the shape registry.
2. **Warnings.** The sweep only checked exit status, so a new warning firing
   across the whole corpus would not have been noticed.
3. **The `.py` companions.** `examples/README.md` promises they show "exactly
   what each Typhon construct lowers to"; nothing verified that.

Both new harnesses run under `cargo test --workspace`, so CI enforces them with
no workflow change. Combined cost: ~5s.

## 6. `examples/errors/` — the new corpus

70 deliberately-broken programs across twelve themed directories, covering
**56 of the 87** emittable codes. Each file is a small realistic program with a
header comment that names its diagnostics, explains the rule, and shows the
fix — the prose is the deliverable; the broken code is the exhibit.

`11-multi-error-programs/` is the "one to many errors" end: `python_habits.ty`
is ordinary Python and every habit Typhon asks you to change; `order_service.ty`
carries ten diagnostics across seven codes; `error_masking.ty` documents C5.

`12-known-gaps/` inverts the format — programs that compile clean and fail at
runtime, one per finding C1–C3. They are asserted to produce *no* diagnostics,
so closing a gap fails the test as a prompt to reclassify the file rather than
letting the record rot.

See `examples/errors/README.md`.

## 7. Recommended follow-ups, in priority order

Ranked by blast radius — how likely a user is to hit it, times how bad it is
when they do.

1. **V1 — inline `?` in the VM.** `tyc run` is the default execution mode and
   inline `?` is documented and idiomatic, so any `Result`-heavy program hits
   this. The VM's `?` expansion needs the structural, bracket-aware treatment
   `as!` already got in v0.15.0.
2. **C1 — the silent missing `await`.** A real soundness hole with a runtime
   crash behind it. The narrow rule (an un-awaited async call flowing into a
   slot annotated with the coroutine's *return* type) keeps deliberate
   deferral legal, and is permitted under the additivity constraint since the
   rejected programs already crash.
3. **F1 — `try`/`except`/`else` false positive.** Rejects correct, idiomatic
   code, and the workaround (hoisting the `else:` body into the `try:`) makes
   the code worse.
4. **V3 — lambda default args in the VM.** The compiler prescribes this exact
   form as the fix for `loop_closure_capture`; following our own advice should
   not crash.
5. **V2 — `max()` tie order.** Silent wrong output, cheap fix (do not replace
   the running best on a tie).
6. **C4 — move the secret-literal scan into `tyc check`,** or amend the CI
   recommendation. Security-relevant and cheap.
7. **S1 — variable-index tuple reads.** Type the read as the union of the
   element types; the constant-index path already works.
8. **V4, V5, V6** — small, self-contained VM fixes with clear expected output
   recorded in `examples/parity/divergent/`.
9. **C2 — extend `implicit_any` to signatures.** Zero measured corpus impact;
   needs an explicit narrowing decision plus a changelog note.
10. **F2 — `case {}:` exhaustiveness**, and **C3 — decide
    `missing_initialiser`'s fate** (wire it up, or retire the code and its
    `tyc explain` entry).
11. **The 77 non-`fmt`-clean example files.** Either reformat and accept losing
    the hand alignment, or document that the corpus is intentionally
    hand-formatted so nobody "fixes" it in a drive-by.
